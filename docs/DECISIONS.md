# 결정 기록

## D-065 기준 캐릭터 교체 의상 선택과 중립색 잔여 진단

- 관측: 새 의상은 생성됐지만 기존 다리 의상·신발과 넓은 중립색 부분이 남았습니다. 과거 보호 분류를 분모에서 제외하는 검사는 기존 옷이 보호로 잘못 분류된 경우에도 포함률 100%를 표시할 수 있었습니다.
- 선택: 생성된 기준 후보에서 기존 SAM2 UI로 교체 의상과 꼬리/귀 등의 특수 보호를 별도 선택합니다. 기준 RGB SHA-256·크기를 검증하고 두 역할의 충돌은 재선택으로 해결합니다. 사용자 승인 경계에는 추가 닫기·팽창을 하지 않으며, 자동 신체 파싱은 머리/얼굴 보호와 진단용으로 유지합니다.
- 검사: 보호 겹침은 분모에서 제외하지 않습니다. 상태를 covered/incomplete/needs_review/not_evaluable로 구분하고 검증 대상이 없으면 비율은 null입니다. 이는 D-041 및 D-045 중 보호 겹침 제외 정의를 대체합니다. 포함률은 선택된 영역의 중립화 범위이지 의상 의미 인식 정확도나 생성 품질 점수가 아닙니다.
- 투명성: 실제 교체 원천, 적용하지 않는 AutoMasker 후보, 보호 충돌 위치를 구분합니다. Inpaint 결과에는 중립색 잔여 후보를 아홉 번째 진단으로 추가하며, 합법적인 회색 의상도 검출될 수 있어 자동 차단하지 않습니다.
- 재사용: 새로운 분할 모델·좌표 변형 엔진은 추가하지 않습니다. SAM2 후보 추출/선택과 기존 NumPy·OpenCV 연산을 재사용합니다. 추가 SAM2 선택 작업으로 전처리 시간은 늘 수 있으며 속도·품질 개선을 보장하지 않습니다.
- 검증 범위: GPU를 호출하지 않는 단위·모의 실행·Qt 승인 테스트로 확인합니다. 실제 사용자 이미지의 잔여 의상 개선 여부는 다음 GPU 실행에서 확인해야 합니다.
- 검증 결과: 일반 회귀 197개, GUI 17개, 기존 SAM2 13개로 총 227개 통과했습니다. 새 SAM2 작업 종료 직후 창 전환의 간헐적 Qt 충돌에 대해 신호를 GUI 큐로 전달하고 종료 동기화 후 다음 이벤트에서 창을 열도록 보강했습니다. GUI 17개를 추가로 세 번 연속 실행하여 모두 통과했습니다. Python 구문 검사와 저장소 줄바꿈 설정을 유지한 Git 공백 검사도 통과했으며 실제 GPU 실행은 0회입니다.
- Qt 근거: [QThread 종료 신호와 wait 동기화](https://doc.qt.io/qtforpython-6/PySide6/QtCore/QThread.html#PySide6.QtCore.QThread.isFinished). 종료 신호만으로 네이티브 정리 완료를 가정하지 않습니다.

- 영향: `prompts.csv`와 기본 생성 수를 3개로 줄입니다. 마음에 드는 결과가 없으면 확인한 실행 폴더만 정리하고 새 실행에서 다시 3장을 생성합니다.

## D-008 Animagine XL 단독 한 장 시험

- 문제: SD 1.5는 구조 확인에는 성공했지만 목표인 2D 애니메이션 선화와 셀 채색에 특화된 기준 모델이 필요합니다.
- 후보: SD 1.5를 바로 교체, 기존 설정을 유지하며 Animagine XL 전용 설정 추가
- 선택: `base.yaml`은 비교용으로 유지하고 `animagine.yaml`을 추가
- 이유: 두 모델의 결과와 메모리 사용량을 비교할 수 있고 기존 성공 경로를 잃지 않습니다.
- 영향: `model.family`으로 SD 1.5와 SDXL 불러오기 방식을 구분합니다. Animagine은 768×768, 한 장, float16, CPU 대피 방식으로 먼저 시험합니다. 참조 그림과 ControlNet은 아직 연결하지 않습니다.
- 확인 결과: 768×768 이미지를 19.719초에 생성했고 최대 GPU 메모리는 5,465,761,280바이트였습니다. 이미지의 선화와 2톤 셀 채색도 정상으로 확인했습니다.

## D-009 서버 없는 Windows 설치형 아이콘 앱

- 선택: Java와 백엔드를 완전히 제외하고 Python Windows 설치형 앱으로 배포
- 이유: 서버를 켜거나 관리하지 않고 참조 그림 선택부터 후보 생성과 저장까지 한 프로그램 안에서 처리할 수 있습니다.
- 영향: 기존 Python 생성 모듈은 유지하며 화면은 생성 기능이 안정된 뒤 연결합니다. Java, 웹 서버, API, DB, 로그인은 추가하지 않습니다. 화면 도구와 설치 도구는 7단계 통과 후 비교하고 결정합니다.

## D-012 1차 출시에서 배경 기능 제외

- 문제: 배경까지 별도 참조하고 제어하면 입력 역할이 늘어나 캐릭터 디자인 유지 검증이 늦어집니다.
- 선택: 1차 출시는 배경 생성과 배경 참조 입력을 제외하고 단색 배경의 캐릭터 생성에 집중
- 이유: Ollama 같은 별도 텍스트 생성 AI 없이 Animagine의 기본 문장 해석 기능만으로 캐릭터 행동을 입력하고, 디자인 일관성을 먼저 확인하기 위해서입니다.
- 영향: 화면에는 배경 입력을 만들지 않습니다. 시험 프롬프트는 단순한 흰색 배경을 사용하며 투명 배경 처리는 생성 품질 확인 후 별도 결정합니다.

## D-013 GUI 이미지 생성 실패 수정

- 문제: IP-Adapter 적용 후 이미지 생성에서 `tuple`에 `shape`가 없다는 오류가 발생하고 GUI가 멈춘 것처럼 보였습니다.
- 원인: IP-Adapter 전용 이미지·문장 처리기를 연결한 뒤 일반 분할 주의 처리(`enable_attention_slicing`)가 이를 덮어썼습니다. 또한 모델 로딩과 생성이 화면 실행 흐름에서 동작했습니다.
- 선택: 분할 주의 처리를 제거하고 PyTorch 2의 기본 효율 처리와 CPU 대피를 유지합니다. 생성 작업은 QThread에서 실행합니다.
- 영향: GUI는 `animagine.yaml`을 명시적으로 사용하고 캐릭터 기준 이미지만 필수로 받습니다. 미구현 의상·자세 버튼은 비활성화하며 모든 오류를 `result.json`과 상세 오류 창에 기록합니다.
- 확인 결과: 자동 테스트 10개와 GUI 생성 검사를 통과했습니다. IP-Adapter 적용 768×768 이미지 한 장을 98.707초에 생성했고 최대 GPU 메모리는 6,171,868,160바이트였습니다.
- 공식 근거: https://huggingface.co/docs/diffusers/api/pipelines/overview
- IP-Adapter 처리기: https://huggingface.co/docs/diffusers/main/api/attnprocessor

## D-014 화면 범위 가드레일

- 문제: 전신 문구가 있어도 정사각형 화면에서는 머리나 발끝이 잘린 결과가 생성될 수 있습니다.
- 후보: 문구만 강화, 화면 비율과 문구를 함께 변경, 사람 관절 인식으로 생성 후 자동 검사
- 선택: 1차로 GUI에 전신, 상반신, 얼굴 중심 선택을 추가하고 각 선택이 화면 비율·필수 표현·제외 표현을 함께 바꾸도록 합니다.
- 전신 기준: 576×896 세로 화면, 머리부터 발끝과 양발이 화면 안에 있어야 하며 일부가 잘린 결과는 사용자가 후보에서 제외합니다.
- 이유: 새 인식 모델 없이 현재 Animagine XL과 IP-Adapter만 사용해 빠르게 잘림 가능성을 낮출 수 있습니다.
- 한계: 생성형 모델의 문장 조건만으로 전신을 100% 보장할 수는 없습니다.
- 다음 기준: 실제 전신 시험에서 계속 잘리면 자세·관절 인식(DWPose)으로 머리와 발목이 모두 검출된 결과만 통과시키는 자동 검사를 별도 단계로 추가합니다.
- 구조 영향: 화면 범위 규칙은 현재 작고 GUI 전용이므로 gui_main.py 한곳에서 관리합니다. 다른 파일이나 새 모델은 추가하지 않습니다.

## D-015 고정 해상도 검사 제거

- 문제: SDXL을 768×768로만 허용한 초기 시험 검사가 전신용 576×896 설정을 차단했습니다.
- 원인: 한 장 기준 생성 시험을 위한 임시 제한이 GUI의 공통 설정 검사에 남아 있었습니다.
- 선택: 특정 가로·세로 조합 대신 모델 처리 단위와 현재 GPU의 안전 범위를 검사합니다.
- 허용 기준: 가로·세로 각각 256 이상, 8의 배수, 한 변 1536 이하, 전체 픽셀 수 1024×1024 이하
- 이유: 정사각형·가로형·세로형을 모두 허용하면서 RTX 4060 8GB에서 지나치게 큰 요청은 실행 전에 안내할 수 있습니다.

- 확인 방법: 512×512, 768×768, 576×896은 통과하고 577×896과 1536×1024는 한글 오류로 거절해야 합니다.

## D-016 GUI 후보 생성 흐름에 하향식 네 블록 적용

- 문제: 오류가 발생한 위치에서 바로 코드를 고치다 보면 화면 파일에 비율·문장·시드 계산이 쌓이고, 생성 파일에 저장 책임까지 섞일 수 있습니다.
- 후보: 현재 함수 안에서 계속 수정, 파일부터 더 잘게 분리, 입력부터 출력까지 큰 역할을 먼저 정한 뒤 필요한 파일만 변경
- 선택: GUI 후보 생성 흐름을 사용자 입력, 데이터 가공, AI 모델 실행, 결과 출력의 네 블록으로 나눕니다.
- 사용자 입력: 기준 이미지와 화면 범위만 받습니다.
- 데이터 가공: 크기, 생성 문장, 제외 문장, 시드와 설정 검사를 모두 끝냅니다.
- AI 모델 실행: 준비된 요청을 받아 후보 이미지 한 장을 메모리로 반환합니다.
- 결과 출력: 후보를 보여주고 사용자가 저장을 승인한 PNG와 JSON만 기록합니다.
- 이유: 비율 문제가 생기면 데이터 가공만, GPU 문제가 생기면 모델 실행만, 저장 문제가 생기면 결과 출력만 확인할 수 있습니다.
- 구조 영향: 데이터 가공을 맡는 `genai_lab/request.py` 한 파일만 새로 계획합니다. `generator.py`에서는 저장 책임을 제거하고 `result.py`는 승인된 결과만 저장하도록 바꿀 예정입니다.
- 기존 결정과의 관계: D-014에서 화면 범위 규칙을 `gui_main.py`에 두기로 한 부분은 이 결정으로 바꿉니다. 화면 범위 선택은 GUI에 남기고, 크기와 문장 변환은 데이터 가공 블록으로 이동합니다.
- 적용 범위: 먼저 GUI 후보 생성 흐름에만 적용하며 기존 `run.py` 명령 실행 경로는 동시에 고치지 않습니다.
- 확인 방법: 데이터 가공은 GPU 없이 화면 범위별 결과를 검사하고, 모델 실행은 파일을 만들지 않은 후보 한 장을 반환하는지 확인하며, 결과 출력은 승인 전 파일이 없는지 검사합니다.
- 현재 상태: 문서로 역할을 확정한 단계이며 Python 구조 변경은 아직 시작하지 않았습니다.

## D-017 업무 대상·세부 의미·객체 종류 순서로 데이터 이름 지정

- 문제: `UserGenerationRequest`, `PreparedGenerationRequest`와 `GenerationCandidate`는 이름만 보고 업무 대상과 데이터 단계를 한 번에 구분하기 어렵습니다.
- 이름 규칙: 업무 대상, 세부 의미, 객체 종류 순서로 작성합니다.
- 선택: `CharacterGenerationInput`, `CharacterGenerationRequest`, `CharacterGenerationCandidate`를 사용합니다.
- 보조 종류: 화면 범위는 `CharacterFramingType`으로 이름을 붙이고 전신, 상반신과 얼굴 중심만 허용합니다.
- 이유: 마지막 단어만 봐도 화면 입력, 모델 실행 요청과 미승인 후보 중 어느 단계인지 확인할 수 있습니다.
- 필드 원칙: 화면 입력에는 사용자 값만, 모델 요청에는 계산이 끝난 값만, 후보에는 정확한 실행 요청과 메모리 이미지·실행 기록만 넣습니다.
- 경계 원칙: 승인·거절과 저장 상태는 모델 실행 후보에 넣지 않고 결과 출력 단계에서 별도로 정의합니다.
- 구현 형태: 세 객체는 로컬 Python 내부 dataclass로 구현하며 이름 없는 `dict`, `list[dict]`, `Any`와 외부 API용 Pydantic 모델은 추가하지 않습니다.
- 상세 계약: `docs/DATA_MODELS.md`에 필드, 생성 위치, AI 실행 여부와 저장 여부를 기록합니다.
- 현재 상태: 데이터 계약을 문서로 확정한 단계이며 Python 구현은 아직 시작하지 않았습니다.

## D-018 원본 캐릭터 유지에 Image-to-Image 적용

- 문제: 전신 구도와 비율은 개선됐지만 기본 IP-Adapter가 색상과 동물 귀 같은 큰 특징만 전달해 얼굴, 머리 장식과 의상 구조가 다른 캐릭터를 생성했습니다.
- 후보: 프롬프트와 참조 강도만 추가 조정, IP-Adapter Plus 즉시 도입, 원본 이미지를 생성 시작 화면으로 사용하는 Image-to-Image 적용
- 선택: 현재 SDXL 모델과 IP-Adapter는 유지하고 원본 전체를 576×896 흰색 화면에 비율대로 배치한 뒤 Image-to-Image로 필요한 만큼만 다시 그립니다.
- 원본 변경 강도: 0.30으로 시작하며 원본 유지 모드에서는 0.15부터 0.35까지만 허용합니다. 이 값과 IP-Adapter 반영 강도 0.80은 별도로 기록합니다.
- 이유: IP-Adapter는 압축된 이미지 특징을 전달하지만 Image-to-Image는 원본 픽셀을 생성 시작점으로 사용하므로 한 장의 원본을 유지하는 현재 목적에 더 직접적입니다.
- 메모리 영향: `AutoPipelineForImage2Image.from_pipe`로 이미 불러온 모델 구성요소를 재사용하고 SDXL CPU 대피를 유지하므로 두 번째 베이스 모델을 올리지 않습니다.
- 적용 범위: 첫 검증은 전신 한 장만 허용합니다. 상반신, 얼굴, 다른 자세와 ControlNet은 결과에 섞지 않습니다.
- 통과 기준: 얼굴, 머리와 눈, 동물 귀와 꼬리, 머리 장식, 망토, 허리 장식, 비대칭 스타킹과 신발의 주요 형태와 색상이 유지되어야 합니다.
- 실패 처리: 모델 실행에 성공해도 다른 캐릭터로 보이면 사용자가 후보를 거절하며 PNG와 JSON은 만들지 않습니다.
- 공식 근거: https://huggingface.co/docs/diffusers/using-diffusers/img2img
- 모델 재사용 근거: https://huggingface.co/docs/diffusers/api/pipelines/auto_pipeline

## D-019 전신 후보의 세부 품질 설정

- 문제: 576×896 전신 후보에서 원본 캐릭터는 유지됐지만 얼굴과 손이 작게 뭉개지고 손·꼬리 경계와 다리 형태가 불안정했습니다. GUI 축소 미리보기 304×476만으로는 실제 생성 품질도 판단하기 어려웠습니다.
- 후보: 변경 강도를 올려 다시 그리기, 세부 보정 모델 즉시 추가, Animagine 공식 세로 해상도와 권장 반복 횟수 적용
- 선택: 원본 변경 강도 0.30과 IP-Adapter 강도 0.80은 유지하고 전신 크기를 768×1344, 반복 횟수를 28로 변경합니다.

- 적용 범위: 전신 한 장만 검증하며 ControlNet과 얼굴·손 부분 재처리는 이번 변경에 포함하지 않습니다.

## D-020 참조 화질 승인과 얼굴·손 제한 보정

- 문제: 참조 이미지가 흐리거나 세부가 작으면 모델이 흐림, 비어 있는 눈, 무너진 손과 옷 주름까지 캐릭터 특징처럼 따라 그릴 수 있습니다. 생성 후 전체를 다시 그리면 캐릭터 디자인이 달라질 위험도 있습니다.
- 선택: 생성 전에 참조 화질을 규칙으로 검사하고, 부족할 때만 애니 그림 확대 복원 모델(RealESRGAN_x4plus_anime_6B)을 실행합니다. 사용자가 원본과 보정본을 비교해 승인한 이미지로만 생성합니다. 생성 후에는 얼굴·손 탐지(YOLO)가 찾은 작은 영역만 부분 재생성(Diffusers Inpaint)하고 보정 전후를 다시 사용자가 선택합니다.
- 처리 순서: 화질 검사 → 필요한 경우 확대 복원 → 사용자 승인 → Animagine과 IP-Adapter 생성 → 얼굴·손 탐지 → 허용 마스크 검사 → 부분 보정 → 마스크 밖 픽셀 불변 검사 → 사용자 선택 → 저장 승인
- 확대 복원의 단점: 선이나 장식을 잘못 추측할 수 있습니다. 보완: 보정본을 자동 채택하지 않고 사용자가 비교 승인하며, 승인하지 않으면 생성을 막습니다.
- 탐지의 단점: 작은 손이나 가려진 얼굴을 놓칠 수 있습니다. 보완: 탐지하지 못하면 전체를 임의로 고치지 않고 생성 원본을 유지하며 로그와 화면 상태로 알립니다.
- 부분 보정의 단점: 얼굴·손을 고치면서 캐릭터 특징이 달라질 수 있습니다. 보완: 면적 상한을 통과한 마스크만 사용하고 마스크 밖 픽셀이 하나라도 바뀌면 보정을 버립니다. 보정 전후 최종 선택은 사용자에게 둡니다.
- 성능의 단점: 확대 복원과 부분 보정 때문에 시간이 늘고 GPU 메모리를 더 사용합니다. 보완: 확대 복원은 타일 단위, 탐지는 CPU, 얼굴·손 보정은 한 영역씩 처리합니다. 실패하면 생성 원본으로 복구합니다.
- 보류: 자세·관절 안내(DWPose/ControlNet)는 다양한 자세가 실제로 실패한다는 근거가 쌓이기 전까지 추가하지 않습니다.
- 배포 전 결정: 현재 YOLO 실행 도구인 Ultralytics는 오픈소스 배포 조건을 확인해야 합니다. 설치형 앱 배포 전에는 전체 앱을 해당 조건과 맞게 공개할지, 상용 라이선스를 구할지, 다른 탐지기로 교체할지 하나를 확정합니다. 프로젝트 라이선스는 이번 구현에서 임의로 정하지 않습니다.
- 공식 근거: https://github.com/xinntao/Real-ESRGAN
- 부분 재생성 안내: https://huggingface.co/docs/diffusers/en/using-diffusers/inpaint
- 탐지 모델 저장소: https://huggingface.co/Bingsu/adetailer
- Ultralytics 라이선스 안내: https://www.ultralytics.com/license


## D-021 의상 합성 보호 경계와 임시 정면 자세 정책

> 현재 상태: 자세 임시 정책은 D-022에서 폐기됐고, 의상 보호 경계는 D-023 구현으로 대체됐습니다.
- 문제: 의상만 바꾸려는 합성 모델이 얼굴, 머리, 손, 발, 노출 피부, 자세와 배경까지 함께 다시 그릴 수 있습니다. 자세 참조 기능이 없는 상태에서 원본의 옆모습이나 앉은 자세를 그대로 받으면 정면 전신 결과도 보장할 수 없습니다.
- 자세 임시 정책: 자세 참조가 사용자 승인 흐름까지 구현되기 전에는 DEFAULT_FRONT_STANDING만 허용합니다. 입력 이미지의 자세는 달라도 되지만 GUI 출력 범위는 전신으로 잠그고 사용자가 정면 스탠딩 출력에 동의해야 생성합니다. Image-to-Image 변경 강도는 0.25에서 0.30으로 올려 원본 자세보다 출력 자세 문구를 반영할 여지를 늘립니다.
- 의상 보호 정책: 의상 분리 결과에서 얼굴·머리·손·발·노출 피부 보호 영역을 뺀 픽셀만 변경할 수 있습니다. 경계 흐림도 이 의상 허용 영역 안에서만 적용합니다.
- 실패 처리: 의상 합성기의 출력 크기가 다르거나 의상 허용 영역 밖의 픽셀이 하나라도 바뀌면 합성 후보를 폐기합니다. 합성 원본, 마스크와 폐기 후보는 자동 저장하지 않습니다.
- 구현 경계: genai_lab/clothing.py에는 의상 합성기가 지킬 입력·출력 계약, 보호 계획, 제한 합성과 픽셀 검사를 구현했습니다. SCHP·WD14·CatVTON은 아직 설치하거나 실행 흐름에 연결하지 않았습니다. 사람·의상 분리 모델이 만든 마스크를 사용자가 확인하는 단계가 확정된 뒤 이 경계에 연결합니다.
- 트레이드오프: 강한 보호 마스크는 신체 변형을 막지만 의상과 피부 경계가 일부 덜 자연스러울 수 있습니다. 이를 보완하는 경계 혼합 마스크도 단단한 의상 허용 마스크 안에서만 작동하게 하여 캐릭터 보호를 우선합니다.

## D-025 의상 추출 전 과정 공개와 원본 픽셀 보존

- 문제: 자동 탐지 사각형과 최종 합성 결과만으로는 의상이 원본 그대로 추출됐는지, 모델이 다른 형태로 변형했는지, 의상을 인식하지 못했는지 구분할 수 없습니다.

- 사용자 선택: 최종 화면은 입력 원본, 위치 사각형, 선택 마스크, 투명 배경 추출본과 흰 배경 확인본 5개를 보여줍니다. 선택지는 추출 승인, 마스크 다시 선택과 의상 사용 취소 3개입니다.

## D-026 떨어진 의상 부위의 복수 영역과 마스크 합치기

## D-028 원본 RGB 추출과 작은 마스크 공백의 제한 복원

- 문제: 마스크를 0 또는 255로 이분화하면 SAM2 경계의 1~254 반투명 값이 사라져 의상 외곽선이 계단처럼 보입니다. 마스크 내부 공백을 모두 채우면 실제 목선·장식 구멍까지 의상으로 잘못 채울 수 있습니다.
- 알파 경계: SAM2 복원은 `binarize=False`로 실행합니다. 확률 1% 이하는 알파 0, 99% 이상은 알파 255, 그 사이는 알파 1~254로 유지합니다. 복수 마스크는 픽셀마다 가장 큰 알파값으로 합칩니다.
- 공백 기준: 이미지 경계와 맞닿지 않은 공백만 검사합니다. 크기는 4,096픽셀과 전체 이미지의 0.250% 중 작은 값 이하, 공백과 주변 의상의 RGB 거리 36.0 이하일 때 복원합니다. 흰 의상은 주변 명도 200.0 이상이고 공백과의 명도 차이가 48.0 이하일 때도 복원합니다.
- RGB 보존: 공백 복원은 색을 생성하지 않고 원본 픽셀의 알파만 128 이상으로 복원합니다. 완성된 RGBA 이미지에서 원본 RGB를 다시 비교하며 변경 허용값은 0개, 보존율은 100.000%입니다.
- 사용자 가드레일: 정규화 원본, 승인 마스크, 공백 처리 후 마스크와 흰 배경 추출본 4개를 한 화면에 표시합니다. 흰 의상 규칙이 실제 구멍을 잘못 복원할 가능성이 있으므로 사용자 승인 전 다음 단계 호출은 0회입니다.
- 미리보기: 전체 크기의 투명 추출본은 메모리에 유지하되 GUI는 알파가 1 이상인 최소 사각형으로 자동 잘라 보여줍니다. 파일 저장은 0개입니다.
