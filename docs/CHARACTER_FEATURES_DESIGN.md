# 2단계 설계: 기준 캐릭터 특징표 → 생성 조건 → 결과 검증 (2026-10-14, 초안)

## 결론부터
- 2단계(완성 기준 "새 작품의 동일성": 특징 유지, 픽셀 아님)의 첫 과제는 **이 캐릭터를 알아보게 하는 특징을 입력에서 공통 능력으로 뽑아, 생성 조건으로 넣고, 결과에서 유지됐는지 확인하는 구조**다(D-118). 부위 분할("여기는 머리, 여기는 옷")만으로는 어떤 머리 특징을 지켜야 이 캐릭터로 보이는지 정해지지 않는다.
- 새 캐릭터마다 사람이 규칙을 만들지 않는다(D-104). 추출은 자동, 확정은 사람이 한 번(부위 체크와 같은 방식), 저장은 캐릭터 파일별.
- 구현 전이다. 이 문서는 설계와 근거만 적는다. 승인 뒤 CPU 추출·검증부터 만들고, 생성 조건 연결은 자유 생성 계약 갱신과 함께 한다.

## 1. 지금 있는 것 / 없는 것
| 필요한 것 | 지금 | 비고 |
|---|---|---|
| 공통 부위 지식 | 있음 — 머리카락·얼굴·눈·몸·옷·꼬리·날개 분할(`parts.npz`), 귀·꼬리·날개 사용자 확정·저장 | 그대로 재사용 |
| 기준 캐릭터 특징표 | **없음** | 이 문서의 대상 |
| 변경 요청 분리 | 있음 — 조건 목록(D-112: 교체 조건 vs 보존 조건, 출처·이유) | 특징표가 보존 조건의 새 출처(`character_features`)가 된다 |
| 결과 검증: 편집 요구 충족 | 일부 — 팔·머리 위치·머리 모양 자동 검사, 기존 옷 잔존은 사람 체크 | 편집 단계용 |
| 결과 검증: 캐릭터 동일성 | **없음(사람 판정 `same_character`뿐)** | 특징표 기준 자동 비교 추가 |
| 신원 측정 | 보고서만 — 피부색·머리색 표본·팔 폭·마름 정도(`identity_measurement`, 작업실 보고 창) | 특징표 추출·검증에 재사용 |

## 2. 특징표(character features)의 항목
캐릭터 파일 하나에 하나. 값마다 **출처**(tags / pixels / user)와 **확정 여부**를 둔다. 묻지 않은 항목은 `unknown`이며 추측해서 채우지 않는다(D-111·D-114 원칙).

| 항목 | 추출 방법(자동) | 값 예 |
|---|---|---|
| 머리 길이·모양 | 태그 분석기(long_hair, twintails, bangs, ahoge …, 문턱 0.5) | twintails, very_long_hair, blunt_bangs |
| 머리색 | 머리카락 분할 영역의 Lab 군집(`hair_shape`와 같은 방법), 주색 1~2개 | 청록(ΔE 군집 중심) |
| 눈 색 | 눈 분할 영역의 주색 + 태그(aqua_eyes …). D-126부터 두 눈을 따로(채도 상위 40% 홍채, 색조 비교, 오드아이) | 청록 |
| 머리 장식 | 태그(hair_ornament, headphones, hat …) + 머리 장식 분할 | headset, 검은 머리끈 |
| 피부색 | 기존 `identity_measurement` 표본 | Lab 값 |
| 체형 특징 | 기존 어깨 폭·마름 정도(체형 판정은 폭만이 아니라 어깨 경사도 함께) | 수치 |
| 부위 | 이미 확정된 귀·꼬리·날개 | ears, tail |
| 성별 | 이미 확정된 값 | female |
| 고유 형태(D-126) | 자동 추출 없음 — 사람이 4개까지 적는 메모(';'로 나눔). 영어 메모만 생성 지시문에, 모든 메모는 결과 확인 체크 | heart-shaped tail tip |

제외: 옷·소품·배경·자세(변경 요청 쪽). 얼굴 생김새 자체는 수치화하지 않는다 — 1단계에서는 원본 픽셀, 2단계에서는 시각 참조(머리 크롭)로 전달한다.

## 3. 확정과 저장
- 추출 결과를 편집·생성 시작 전 확인 창에 "이 캐릭터의 특징"으로 보여 주고 사람이 고치거나 승인한다(부위 체크와 같은 흐름). 승인값은 `character_preferences`에 캐릭터 파일 기준으로 저장, 다음 실행에 미리 채움.
- `trace.json`의 `input_facts.character_features`에 값·출처·확정 여부를 남긴다.

## 4. 생성 조건으로 쓰기
- 조건 목록에 출처 `character_features`인 보존 조건을 추가한다: "The character has {twin tails of very long aqua hair with blunt bangs}, {aqua eyes}, {a black headset}; keep them exactly." 값이 `unknown`인 항목은 문장에 넣지 않는다.
- 시각 참조: 머리 크롭(원본)을 참조 그림으로 함께 전달한다(시각 조건 우선, 문장은 보조).
- 자유 생성(자세·구도·배경·문장)의 계약 갱신 때 이 조건이 기본 보존 조건이 된다. 편집 단계는 지금 그대로(픽셀 붙이기)이며, 특징 검증이 안정되면 그때 바꾼다.

## 5. 결과 검증
- 자동: 결과에 같은 추출을 돌려 항목별 `kept / changed / missing / unknown`을 적는다(머리 길이·모양 태그 일치, 머리색·눈 색 ΔE 문턱, 장식 태그 유무, 부위 유무). 문턱은 평가 세트로 정하고 그림별로 바꾸지 않는다.
- 사람: `same_character`는 사람 판정이 최종. 자동 결과는 판정을 돕는 근거이지 대체가 아니다.
- 판정 기록은 지금 구조(`judgement.json`, D-114)에 항목을 더한다.

## 6. 평가 방법(학습 자료가 아니라 평가 자료)
- 같은 캐릭터의 여러 의상·자세 그림(예: 널리 알려진 캐릭터 3장): 추출된 특징표가 그림마다 같은 값으로 나오는가(추출의 일관성), 다른 캐릭터와는 다르게 나오는가(구별력).
- 처음 보는 창작 캐릭터: 알려진 캐릭터 성공만으로 일반화를 주장하지 않는다. 생성 결과에서 특징 유지 자동 판정과 사람 판정의 일치율을 잰다.
- 동일성을 **판단**하는 능력과 생성 중에 **지키는** 능력은 별개다. 전자는 CPU로 먼저 확정하고, 후자는 생성 조건 연결 뒤 GPU로 잰다(장수는 작게, 실패 유형 중심).

## 7. 하지 않는 것
- 캐릭터별 규칙·문턱 조정. 분류군(이미지 모음) 저장만으로 능력이 생긴다고 보지 않는다.
- RAG·외부 LLM(현 단계 비추천, D-113·D-110).
- 얼굴 임베딩 모델 추가 도입은 평가 세트로 필요성이 확인된 뒤 검토.

## 8. 다음 순서(2026-10-14 승인)
1. CPU 추출기 `character_features.py` — **완료(D-119·D-120)**: 추출·파일 저장·실행 스크립트, 확인 창 미리 채움(글 상자)·캐릭터별 저장·실행 기록(`character-features/features.json`, trace).
2. 결과 검증기 — **완료(D-121)**: `character_verification.py`, 시도마다 verification.json·trace 기록, `scripts/verify_character_features.py`로 저장 실행 대조. 한계: 부위 개수·모양은 태그로 못 봄(사람 판정 유지), 픽셀 비교는 원본 마스크 기준이라 같은 구도에서만.
3. 평가 세트로 추출 일관성·구별력 측정(CPU) — 같은 캐릭터 다른 의상·자세 그림 필요(사용자 제공 대기). 결과 쪽 분할(꼬리 개수 등)은 이때 함께 설계.
4. 자유 생성 계약 갱신 때 조건 연결(GPU 시험은 그때 설계).
