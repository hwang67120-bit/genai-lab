# RAG(사례 검색) 도입 타당성 검토 (2026-10-13, Claude, 읽기 전용)

**결론: 현 단계 도입 비추천.** 사례를 검색해 참고하는 방식이 지금의 "사람 수정"을 줄여 준다는 근거를 저장된 자료에서 찾지 못했다. 반복 조정의 원인 대부분이 **생성 모델이 적절한 조건을 따르지 못한 것**이고, 조건 선택 자체는 이미 입력 사실(성별·귀·꼬리·날개) 확인 한 번으로 끝나기 때문이다. 사례 수(캐릭터 6명 + 여성 머리 6명 + 너구리)가 적고 실패 유형이 서로 달라, 검색해도 "비슷한 사례"가 없다. 대신 **특징별 사례표(한 장짜리 표)**로 같은 효과를 얻을 수 있는지 먼저 보는 것이 맞다.

- 이 검토는 코드·설정·결과를 수정하지 않았고 GPU를 쓰지 않았다. 유일하게 **실제로 실행한 것**은 태그 분석기를 CPU에서 6장에 돌려 자동 추정값을 확인한 것(§3-2)이다. 나머지는 저장된 자료를 읽고 판단한 것이다.
- 조건 선택이 개선될 가능성(§6 후속 검증)과 이미지 품질이 좋아졌다는 주장은 다르다. 이 문서는 후자를 주장하지 않는다.

## 3. 현재 기록이 검색 근거로 충분한가

### 3-1. 연결 상태
- 요청 16부터 `conditions.json`·`trace.json`이 입력 사실(출처·present/absent/unknown) → 조건(출처·이유) → 시도별 자동 검사 → 자동 판정을 잇는다(D-112). **사람 판정은 아직 이 기록에 연결되지 않는다** — 보고서 본문(마크다운)에만 있고, 어느 항목(꼬리·옷·자세)이 통과/실패인지 구조화돼 있지 않다.
- 요청 14·15는 `request.json`(문자열)과 보고서뿐이다. 조건별 출처는 사후에 D-106~D-111로 재구성해야 한다.
- 자동 검사 통과(합성됨)와 품질 통과는 분리돼 있다. 예: 요청 16 S04 두 벌은 합성됐지만 꼬리 모양·흰 끝은 다르다(Codex 관찰). 이 구분을 검색 자료에 넣으려면 사람 판정이 항목별로 저장돼야 한다.

### 3-2. 실제로 실행한 확인: 자동 추정은 얼마나 맞나 (CPU, 태그 분석기, 6장)

## 5. 도입 비용과 위험

- **잘못된 사례 검색**: K처럼 겉모습이 비슷한 과거 사례(W3 재킷)가 다른 결과를 냈다. 유사도 검색은 "비슷해 보이는" 것을 찾지 "같은 이유로 실패하는" 것을 찾지 않는다.
- **오래된 설정 재사용**: 지시문·검사 규칙이 요청 12→16 사이 5번 바뀌었다. 과거 사례의 성공·실패는 그때의 규칙 아래 결과라, 지금 규칙에 그대로 쓰면 틀린다. 재현성(같은 입력 → 같은 조건)이 검색 자료가 바뀔 때마다 흔들린다 — D-104의 "그림별 조정 금지"와 충돌한다.
- **실패 기록 오해석**: 자동 합성 통과를 품질 성공으로 넣으면(요청 16 S04) 검색 자료가 오염된다. 사람 판정이 항목별로 저장되기 전에는 검색 자료의 정답이 없다.
- **관리 비용**: 임베딩·벡터 DB·갱신·평가 세트가 필요하다. 현재 사례 13명(수인 4 + 여성 6 + K + 너구리 + W1)으로는 검색 품질을 평가할 수도 없다.
- **더 단순한 대안으로 충분한가**: 그렇다고 본다. 자동 특징(§3-2의 sitting·jacket·mechanical_tail·multiple_tails·긴 머리 태그)과 실패 유형의 대응표는 **열 줄 안팎의 표**이며, 검색 없이 "이 그림은 앉은 자세라 머리 크기가 바뀔 수 있습니다"처럼 **시작 전 경고**를 줄 수 있다. 이것은 조건을 바꾸는 게 아니라 사용자에게 지원 범위를 알리는 것이라 D-104와도 맞는다.

## 6. 추천 방향과 가장 작은 후속 검증

추천 방향(도입이 아니라 순서):
1. **사람 판정을 구조화해 trace에 연결**(항목별: 같은 캐릭터 / 옷 같음·일부·다름 / 꼬리 / 옷 잔존 / 자세 / 심한 이상). 이것 없이는 어떤 검색·표도 정답이 없다. 비용 작음(JSON 한 장).
2. **특징별 사례표**(코드 아님, 문서): 자동 특징 → 알려진 실패 유형 → 시작 전 경고 문구. 지금 자료로 쓸 수 있는 줄: `sitting`(S08: 머리 크기 변화·합성 거부), `jacket/coat`가 걸친 형태(K: 잔존), `mechanical_*`(S06: 미교체), 긴 머리·작은 얼굴(S07·W1: 특징점 부족), 꼬리가 가는 수인(S04: 형태 변형).
3. 이미지 유사도 검색(RAG)은 **표의 줄이 20개를 넘고, 태그로 표현되지 않는 특징이 실패를 가르는 것이 확인될 때** 다시 검토한다. 지금은 그 조건이 아니다.

가장 작은 후속 검증 하나(저장 자료만, GPU 없음):
- 특징별 사례표 초안을 **요청 16 결과를 보기 전 상태의 자료(요청 14·15)**로만 만들고, 요청 16의 7장에 대해 "경고가 떴어야 할 장"을 미리 적은 뒤 Codex 관찰과 대조한다.
- 성공 기준: 요청 16의 실패 5장(S08×2 자세, S06 옷, K×2 잔존) 중 **4장 이상**이 표의 경고에 해당하고, 통과 2장(S04×2 머리 합성)에 **잘못된 경고가 0건**.
- 중단 기준: 경고가 맞은 장이 2장 이하이거나, 통과 장에 경고가 붙으면 표도 보류하고 사람 판정 구조화(1번)만 한다.
- 주의: 이것은 "경고의 적중"을 재는 것이지 이미지 품질 개선이 아니다. 경고가 조건 변경으로 이어지려면 그 조건이 공통 규칙으로 정당화돼야 한다(D-104).

## 7. 확인된 사실 / 가설 / 미확인

- **확인된 사실**: 요청 14~16에서 지정한 조건(성별·부위)은 모두 정답이었다(명령 인자·그림). 사람 수정 8건 중 조건 선택 오류는 1건이고 규칙으로 닫혔다. 자동 추정은 성별 6/6, 부위 5/6(CPU 실행). 같은 조건·같은 seed에서 S08 결과가 요청 15와 16에서 달랐다(보고서 16 대조). conditions/trace 기록은 요청 16부터 있다.
- **가설**: 특징별 사례표로 시작 전 경고를 주면 사용자가 실패를 예상하고 입력을 바꾸거나 결과를 빨리 버릴 수 있어 체감 수정 부담이 준다(미검증). 이미지 유사도는 태그보다 나은 실패 예측을 주지 못한다(미검증, 자료 부족).
- **미확인**: 요청 16의 사용자 품질 판정. 너구리 시험의 저장 기록 위치. 사례 수가 30~50장이 되면 결론이 바뀔 수 있는지(현재는 알 수 없음).
