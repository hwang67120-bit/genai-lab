# 결정 기록

## D-001 Windows 직접 실행

- 문제: 개발 원칙은 Linux였지만 사용 가능한 GPU가 Windows의 RTX 4060 8GB에 있습니다.
- 후보: WSL2, 별도 Linux GPU, Windows 직접 실행
- 선택: Windows에서 Python 직접 실행
- 이유: 현재 GPU를 가장 빠르게 사용하고 초기 구조 학습에 집중하기 위해서입니다.
- 영향: 이 프로젝트에 한해 Linux 전용 코딩 원칙의 예외로 둡니다.

## D-002 Stable Diffusion 1.5와 512×512

- 문제: 8GB GPU에서 구조 학습과 안정적인 첫 실행이 필요합니다.
- 후보: SD 1.5, SDXL
- 선택: SD 1.5와 512×512
- 이유: 모델과 참조 그림 전달 장치를 함께 올릴 때 메모리 부담이 비교적 작습니다.
- 영향: 품질보다 전체 흐름 이해와 재현성을 먼저 검증합니다.

## D-003 한 장씩 순차 생성

- 문제: 여러 장을 동시에 생성하면 GPU 메모리가 부족할 수 있습니다.
- 선택: 요청을 한 줄씩 처리하고 매번 바로 저장
- 이유: 중간 결과를 보존하고 실패 위치를 알 수 있습니다.
- 영향: 총 실행 시간은 늘지만 안정성과 재시작이 쉬워집니다.

## D-004 requirements.txt 추가

- 문제: 계획 구조에 설치 목록 파일이 없으면 같은 환경을 재현할 수 없습니다.
- 후보: README에만 기록, 설치 목록 파일 추가
- 선택: `requirements.txt` 추가
- 이유: 도구 버전을 코드와 함께 관리하기 위해 필요합니다.
- 영향: PyTorch는 CUDA 전용 저장소를 사용하므로 README의 별도 명령으로 먼저 설치합니다.

## 보류 결정

- 그림체 학습용 추가 가중치(LoRA): 한 장 참조 결과가 부족하다고 평가된 뒤 결정
- 구조 안내 기능(ControlNet): 포즈와 구도 문제가 확인된 뒤 결정
- 역할별 Python 파일 분리: 기준 이미지 한 장 생성 성공 뒤 결정

## D-005 Windows 인증서 저장소 사용

- 문제: Python의 오래된 인증서 묶음으로 PyPI와 Hugging Face 연결이 실패했습니다.
- 후보: 인증서 검사 끄기, Windows 인증서 저장소 사용
- 선택: `truststore`로 Windows 인증서 저장소 연결
- 이유: 인증서 검사를 유지하면서 Windows가 신뢰하는 인증서를 Python에서도 사용합니다.
- 영향: 프로그램 시작 시 모델 다운로드 전에 인증서 저장소를 연결합니다.

## D-006 기준 생성 성공 후 네 역할 분리

- 확인 결과: 512×512 기준 이미지가 4.686초에 생성됐고 최대 GPU 메모리는 3,415,804,928바이트였습니다.
- 문제: 검증된 `run.py`가 길어져 전체 순서와 세부 처리를 구분할 필요가 생겼습니다.
- 선택: 모델, 참조 그림, 순차 생성, 결과 저장의 네 역할만 분리
- 이유: 실제 실행으로 확인된 책임만 나누면 계획에 없는 추상 구조가 생기지 않습니다.
- 영향: `run.py`는 설정 검사와 실행 순서만 담당하며 생성 동작과 명령은 그대로 유지합니다.

## D-007 초기 후보를 3장으로 제한

- 문제: 초기 설정이 충분히 다듬어지지 않은 상태에서 20장을 만들면 시간과 저장 공간을 쓰고도 채택할 결과가 없을 수 있습니다.
- 후보: 20장을 계속 생성, 한 장만 생성, 후보 3장을 생성하고 직접 선택
- 선택: 실행할 때마다 후보 3장을 한 장씩 순서대로 생성
- 이유: 결과의 차이를 비교할 수 있으면서도 요청 문장과 설정을 빠르게 수정할 수 있습니다.
- 영향: `prompts.csv`와 기본 생성 수를 3개로 줄입니다. 마음에 드는 결과가 없으면 확인한 실행 폴더만 정리하고 새 실행에서 다시 3장을 생성합니다.

## D-008 Animagine XL 단독 한 장 시험

- 문제: SD 1.5는 구조 확인에는 성공했지만 목표인 2D 애니메이션 선화와 셀 채색에 특화된 기준 모델이 필요합니다.
- 후보: SD 1.5를 바로 교체, 기존 설정을 유지하며 Animagine XL 전용 설정 추가
- 선택: `base.yaml`은 비교용으로 유지하고 `animagine.yaml`을 추가
- 이유: 두 모델의 결과와 메모리 사용량을 비교할 수 있고 기존 성공 경로를 잃지 않습니다.
- 영향: `model.family`으로 SD 1.5와 SDXL 불러오기 방식을 구분합니다. Animagine은 768×768, 한 장, float16, CPU 대피 방식으로 먼저 시험합니다. 참조 그림과 ControlNet은 아직 연결하지 않습니다.
- 확인 결과: 768×768 이미지를 19.719초에 생성했고 최대 GPU 메모리는 5,465,761,280바이트였습니다. 이미지의 선화와 2톤 셀 채색도 정상으로 확인했습니다.

## D-009 서버 없는 Windows 설치형 아이콘 앱

- 문제: 백엔드 서버는 실행과 관리 부담이 크고, 사용 목적은 사용자가 직접 아이콘을 빠르게 만드는 것입니다.
- 후보: Java 백엔드 서비스, 브라우저 기반 로컬 서버, Python Windows 설치형 앱
- 선택: Java와 백엔드를 완전히 제외하고 Python Windows 설치형 앱으로 배포
- 이유: 서버를 켜거나 관리하지 않고 참조 그림 선택부터 후보 생성과 저장까지 한 프로그램 안에서 처리할 수 있습니다.
- 영향: 기존 Python 생성 모듈은 유지하며 화면은 생성 기능이 안정된 뒤 연결합니다. Java, 웹 서버, API, DB, 로그인은 추가하지 않습니다. 화면 도구와 설치 도구는 7단계 통과 후 비교하고 결정합니다.

## D-010 설명 가능한 바이브 코딩과 오픈소스 우선

- 문제: 짧은 기간에 모든 기능을 직접 만들면 이미 해결된 문제를 반복하고, AI가 만든 코드를 이해하지 못한 채 구조가 복잡해질 수 있습니다.
- 후보: 모든 기능 직접 구현, AI 코드 무검증 사용, 검증된 오픈소스를 계획에 따라 조립하고 설명
- 선택: 공식 문서와 라이선스를 확인한 오픈소스를 우선 사용하고 AI로 구현 속도를 높이되, 사용자가 구조와 선택 이유를 설명할 수 있을 때만 채택
- 이유: 바퀴를 다시 만들지 않으면서도 프로젝트의 제어권과 배움을 유지할 수 있습니다.
- 영향: 새 도구를 추가하기 전에 기존 도구로 해결 가능한지 확인합니다. 추가한 기능은 목적·입력·처리·출력·실패 조건·확인 방법을 기록하고 단계별 테스트를 통과해야 합니다.

## D-011 작업시간 20~35시간의 초고속 1차 출시

- 문제: 인력이 부족한 상황에서 주 단위 계획은 출시 시점이 너무 늦습니다.
- 후보: 4주 개발, 장시간 노동으로 모든 기능 동시 개발, 출시 기능을 고정한 3~5일 집중 개발
- 선택: 작업시간 20~35시간 안에 참조 입력·후보 3장·선택 저장·Windows 설치만 완성
- 이유: 사람의 무리한 노동이나 테스트 생략이 아니라 이미 검증된 오픈소스 재사용과 범위 제한으로 시간을 줄일 수 있습니다.
- 영향: 화면 꾸미기, LoRA, ControlNet, 편집과 대량 생성은 출시를 막는 문제가 아니면 뒤로 미룹니다. 각 핵심 단계는 짧아도 반드시 한 번의 실제 실행 시험을 통과합니다.
## D-012 1차 출시에서 배경 기능 제외

- 문제: 배경까지 별도 참조하고 제어하면 입력 역할이 늘어나 캐릭터 디자인 유지 검증이 늦어집니다.
- 선택: 1차 출시는 배경 생성과 배경 참조 입력을 제외하고 단색 배경의 캐릭터 생성에 집중
- 이유: Ollama 같은 별도 텍스트 생성 AI 없이 Animagine의 기본 문장 해석 기능만으로 캐릭터 행동을 입력하고, 디자인 일관성을 먼저 확인하기 위해서입니다.
- 영향: 화면에는 배경 입력을 만들지 않습니다. 시험 프롬프트는 단순한 흰색 배경을 사용하며 투명 배경 처리는 생성 품질 확인 후 별도 결정합니다.

## D-013 GUI 이미지 생성 실패 수정

- 문제: IP-Adapter 적용 후 이미지 생성에서 `tuple`에 `shape`가 없다는 오류가 발생하고 GUI가 멈춘 것처럼 보였습니다.
- 원인: IP-Adapter 전용 이미지·문장 처리기를 연결한 뒤 일반 분할 주의 처리(`enable_attention_slicing`)가 이를 덮어썼습니다. 또한 모델 로딩과 생성이 화면 실행 흐름에서 동작했습니다.
- 선택: 분할 주의 처리를 제거하고 PyTorch 2의 기본 효율 처리와 CPU 대피를 유지합니다. 생성 작업은 QThread에서 실행합니다.
- 영향: GUI는 `animagine.yaml`을 명시적으로 사용하고 캐릭터 기준 이미지만 필수로 받습니다. 미구현 의상·자세 버튼은 비활성화하며 모든 오류를 `result.json`과 상세 오류 창에 기록합니다.
- 확인 결과: 자동 테스트 10개와 GUI 생성 검사를 통과했습니다. IP-Adapter 적용 768×768 이미지 한 장을 98.707초에 생성했고 최대 GPU 메모리는 6,171,868,160바이트였습니다.
- 공식 근거: https://huggingface.co/docs/diffusers/api/pipelines/overview
- IP-Adapter 처리기: https://huggingface.co/docs/diffusers/main/api/attnprocessor

## D-014 화면 범위 가드레일

- 문제: 전신 문구가 있어도 정사각형 화면에서는 머리나 발끝이 잘린 결과가 생성될 수 있습니다.
- 후보: 문구만 강화, 화면 비율과 문구를 함께 변경, 사람 관절 인식으로 생성 후 자동 검사
- 선택: 1차로 GUI에 전신, 상반신, 얼굴 중심 선택을 추가하고 각 선택이 화면 비율·필수 표현·제외 표현을 함께 바꾸도록 합니다.
- 전신 기준: 576×896 세로 화면, 머리부터 발끝과 양발이 화면 안에 있어야 하며 일부가 잘린 결과는 사용자가 후보에서 제외합니다.
- 이유: 새 인식 모델 없이 현재 Animagine XL과 IP-Adapter만 사용해 빠르게 잘림 가능성을 낮출 수 있습니다.
- 한계: 생성형 모델의 문장 조건만으로 전신을 100% 보장할 수는 없습니다.
- 다음 기준: 실제 전신 시험에서 계속 잘리면 자세·관절 인식(DWPose)으로 머리와 발목이 모두 검출된 결과만 통과시키는 자동 검사를 별도 단계로 추가합니다.
- 구조 영향: 화면 범위 규칙은 현재 작고 GUI 전용이므로 gui_main.py 한곳에서 관리합니다. 다른 파일이나 새 모델은 추가하지 않습니다.
- 확인 방법: 각 선택의 크기와 문구 단위 테스트, GUI 목록 생성 검사, 전신 실제 생성 결과의 머리·발끝 육안 확인
- 공식 모델 사용 안내: https://huggingface.co/cagliostrolab/animagine-xl-3.1
- SDXL 파이프라인 입력 안내: https://huggingface.co/docs/diffusers/api/pipelines/stable_diffusion/stable_diffusion_xl

## D-015 고정 해상도 검사 제거

- 문제: SDXL을 768×768로만 허용한 초기 시험 검사가 전신용 576×896 설정을 차단했습니다.
- 원인: 한 장 기준 생성 시험을 위한 임시 제한이 GUI의 공통 설정 검사에 남아 있었습니다.
- 선택: 특정 가로·세로 조합 대신 모델 처리 단위와 현재 GPU의 안전 범위를 검사합니다.
- 허용 기준: 가로·세로 각각 256 이상, 8의 배수, 한 변 1536 이하, 전체 픽셀 수 1024×1024 이하
- 이유: 정사각형·가로형·세로형을 모두 허용하면서 RTX 4060 8GB에서 지나치게 큰 요청은 실행 전에 안내할 수 있습니다.
- 구조 영향: GUI에 예외 처리를 추가하지 않고 공통 validate_config 함수 한곳만 수정합니다.
- 확인 방법: 512×512, 768×768, 576×896은 통과하고 577×896과 1536×1024는 한글 오류로 거절해야 합니다.
- 공식 근거: https://huggingface.co/docs/diffusers/api/pipelines/stable_diffusion/stable_diffusion_xl

## D-016 GUI 후보 생성 흐름에 하향식 네 블록 적용

- 문제: 오류가 발생한 위치에서 바로 코드를 고치다 보면 화면 파일에 비율·문장·시드 계산이 쌓이고, 생성 파일에 저장 책임까지 섞일 수 있습니다.
- 후보: 현재 함수 안에서 계속 수정, 파일부터 더 잘게 분리, 입력부터 출력까지 큰 역할을 먼저 정한 뒤 필요한 파일만 변경
- 선택: GUI 후보 생성 흐름을 사용자 입력, 데이터 가공, AI 모델 실행, 결과 출력의 네 블록으로 나눕니다.
- 사용자 입력: 기준 이미지와 화면 범위만 받습니다.
- 데이터 가공: 크기, 생성 문장, 제외 문장, 시드와 설정 검사를 모두 끝냅니다.
- AI 모델 실행: 준비된 요청을 받아 후보 이미지 한 장을 메모리로 반환합니다.
- 결과 출력: 후보를 보여주고 사용자가 저장을 승인한 PNG와 JSON만 기록합니다.
- 이유: 비율 문제가 생기면 데이터 가공만, GPU 문제가 생기면 모델 실행만, 저장 문제가 생기면 결과 출력만 확인할 수 있습니다.
- 구조 영향: 데이터 가공을 맡는 `genai_lab/request.py` 한 파일만 새로 계획합니다. `generator.py`에서는 저장 책임을 제거하고 `result.py`는 승인된 결과만 저장하도록 바꿀 예정입니다.
- 기존 결정과의 관계: D-014에서 화면 범위 규칙을 `gui_main.py`에 두기로 한 부분은 이 결정으로 바꿉니다. 화면 범위 선택은 GUI에 남기고, 크기와 문장 변환은 데이터 가공 블록으로 이동합니다.
- 적용 범위: 먼저 GUI 후보 생성 흐름에만 적용하며 기존 `run.py` 명령 실행 경로는 동시에 고치지 않습니다.
- 확인 방법: 데이터 가공은 GPU 없이 화면 범위별 결과를 검사하고, 모델 실행은 파일을 만들지 않은 후보 한 장을 반환하는지 확인하며, 결과 출력은 승인 전 파일이 없는지 검사합니다.
- 현재 상태: 문서로 역할을 확정한 단계이며 Python 구조 변경은 아직 시작하지 않았습니다.
