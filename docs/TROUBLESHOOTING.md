# 내가 배운 과정과 문제 해결 기록

## 이 문서의 목적

이 문서는 AI가 내 실력을 평가하는 문서가 아니다. 프로젝트를 진행하면서 내가 실제로 질문한 내용, 막힌 지점, 직접 선택한 방향과 이해하게 된 내용을 기록한다.

완성된 결과만 적지 않는다. 왜 문제가 생겼는지 몰랐던 순간과 판단을 바꾼 이유도 남긴다. 나중에 이 문서를 보면 코드를 얼마나 많이 만들었는지가 아니라, 내가 프로젝트의 구조와 선택 이유를 어디까지 설명할 수 있게 됐는지 확인할 수 있어야 한다.

## 작성 기준

다음 중 하나가 실제로 발생했을 때 기록을 추가한다.

- 실행 오류의 원인을 확인하고 해결했을 때
- 생성 결과를 보고 기존 계획을 바꿨을 때
- 여러 방법 중 하나를 선택하고 이유를 확정했을 때
- 내가 기능의 역할이나 구조를 내 말로 설명할 수 있게 됐을 때
- 실패한 방법을 다시 사용하지 않을 기준이 생겼을 때

다음 내용은 기록하지 않는다.

- 내가 확인하지 않은 AI의 추측
- 아직 실행하지 않은 기능을 성공한 것처럼 표현한 내용
- 전문가, 숙련자 같은 근거 없는 평가
- 내 대화에 없었던 생각을 자연스럽게 보이도록 추가한 내용
- 어려운 표현만 바꿔 붙인 설명

새 기록은 다음 순서를 사용한다.

1. 막힌 점
2. 내가 처음 생각한 내용
3. 직접 확인한 내용
4. 내가 정한 방향
5. 지금 설명할 수 있는 내용
6. 아직 확인하지 못한 내용

## 1. 프로젝트 범위를 줄인 과정

### 막힌 점

처음 로드맵은 이미지 생성뿐 아니라 백엔드와 여러 기능까지 포함하여 프로젝트가 너무 커질 수 있었다. 서버를 직접 켜고 관리하는 방식도 내가 실제로 사용하려는 목적과 맞지 않았다.

### 내가 처음 생각한 내용

처음에는 최종 결과를 백엔드로 만드는 방향도 생각했다. 하지만 내가 원하는 것은 다른 서비스를 운영하는 일이 아니라, 기준 이미지를 넣고 아이콘 후보를 편하게 만드는 프로그램이었다.

### 직접 확인한 내용

기능을 계속 추가하면 구조를 이해하기 전에 파일과 역할이 늘어난다. 계획하지 않은 기능을 먼저 넣으면 나중에 내가 흐름을 설명하기 어려워진다는 점을 대화 과정에서 계속 확인했다.

### 내가 정한 방향

- Java와 백엔드는 제외한다.
- 웹 서버, DB, API와 로그인은 만들지 않는다.
- Windows에서 실행하는 설치형 프로그램을 목표로 한다.
- 첫 버전은 기준 이미지, 후보 생성, 사용자 판단과 선택 저장에 집중한다.

### 지금 설명할 수 있는 내용

프로젝트 범위를 줄이는 것은 기능을 포기하는 일이 아니라, 내가 실제로 사용할 핵심 흐름을 먼저 완성하기 위한 선택이라고 설명할 수 있다.

## 2. AI가 추천한 도구를 그대로 넣지 않기로 한 과정

### 막힌 점

이미지 생성 도구를 찾는 과정에서 이미지 프로젝트에 필요하지 않은 텍스트용 AI가 제안되거나, 처음 예상하지 않은 유료 서비스가 함께 제안됐다. ComfyUI, Stable Diffusion WebUI와 Fooocus 같은 완성된 화면 도구도 후보로 나왔다.

### 내가 처음 생각한 내용

오픈소스를 최대한 활용하면 개발 속도를 높일 수 있다고 생각했다. 동시에 유명한 도구라는 이유만으로 프로젝트에 모두 넣으면 구조가 다시 커질 수 있다는 문제가 있었다.

### 직접 확인한 내용

- 텍스트 생성 AI는 현재 이미지 생성 흐름에 필요하지 않다.
- 완성된 다른 화면 도구를 프로젝트 안에 넣으면 내가 만드는 GUI와 역할이 겹친다.
- 이미 존재하는 기능은 참고할 수 있지만, 프로젝트 전체를 다른 도구의 구조에 맞출 필요는 없다.

### 내가 정한 방향

- 텍스트용 AI는 제외한다.
- ComfyUI, Stable Diffusion WebUI와 Fooocus는 현재 앱에 합치지 않는다.
- 필요한 기능과 구현 방법은 참고하되, GenAI Lab의 실행 흐름은 작게 유지한다.
- 품질 문제가 확인되기 전에는 LoRA와 자세 제어 기능을 미리 추가하지 않는다.

### 지금 설명할 수 있는 내용

오픈소스를 활용한다는 것은 모든 도구를 설치하는 것이 아니다. 이미 검증된 기능은 가져오되, 현재 목표에 필요하지 않은 화면과 기능은 제외해야 한다는 점을 설명할 수 있다.

## 3. 모델의 역할을 구분한 과정

### 막힌 점

Stable Diffusion, Animagine XL, IP-Adapter와 ControlNet이 한꺼번에 언급되면서 어떤 모델이 실제 그림을 만들고 어떤 기능이 기준 이미지를 반영하는지 구분하기 어려웠다.

### 내가 처음 생각한 내용

처음에는 모델 파일을 모두 설치하면 기준 캐릭터와 자세가 한 번에 유지될 수 있다고 생각할 수 있었다.

### 직접 확인한 내용

- Animagine XL은 기본 이미지를 만드는 역할이다.
- IP-Adapter는 기준 이미지의 특징을 생성 과정에 전달한다.
- 자세 제어 기능은 구도와 자세가 계속 실패할 때 검토할 별도 역할이다.
- 같은 캐릭터처럼 보이게 하는 문제와 전신이 잘리지 않게 만드는 문제는 서로 다르다.

### 내가 정한 방향

첫 단계에서는 Animagine XL과 기준 이미지 특징 전달 기능을 사용한다. 자세 제어 기능은 전신 구도 실패가 반복되고 필요성이 확인됐을 때만 추가한다.

### 지금 설명할 수 있는 내용

기본 모델, 기준 이미지 반영과 자세 제어는 서로 다른 문제를 맡는다. 한 모델을 추가한다고 캐릭터 유지와 구도 문제가 모두 해결되는 것은 아니라고 설명할 수 있다.

## 4. 실행 위치 오류를 이해한 과정

### 막힌 점

PowerShell에서 GUI를 실행했을 때 다음 오류가 발생했다.

```text
C:\Program Files\Python310\python.exe: can't open file 'C:\Users\user\gui_main.py'
```

### 내가 처음 생각한 내용

가상 환경이나 Python 설치가 잘못된 문제처럼 보일 수 있었다.

### 직접 확인한 내용

Python은 현재 PowerShell 위치인 `C:\Users\user`에서 `gui_main.py`를 찾고 있었다. 실제 파일은 네트워크의 GenAI Lab 프로젝트 폴더에 있었다.

### 내가 정한 방향

실행 전에 프로젝트 폴더로 이동하거나, Python 실행 명령에 프로젝트 파일의 전체 경로를 사용한다.

### 지금 설명할 수 있는 내용

Python 실행 파일의 위치와 실행할 `.py` 파일의 위치는 다른 개념이다. 가상 환경의 Python을 선택해도 현재 폴더가 자동으로 프로젝트 폴더로 바뀌지는 않는다고 설명할 수 있다.

## 5. 컴퓨터 메모리와 그래픽카드 메모리를 구분한 과정

### 막힌 점

RTX 4060의 성능은 괜찮지만 그래픽카드 메모리가 8GB라서 SDXL 모델을 실행할 수 있는지 걱정했다. 컴퓨터 메모리 32GB를 함께 사용하면 부족한 부분을 채울 수 있는지도 확인할 필요가 있었다.

### 내가 처음 생각한 내용

컴퓨터 메모리가 충분하면 그래픽카드 메모리 부족을 그대로 대신할 수 있을 것이라고 생각할 수 있었다. 반대로 단순 계산만 보고 8GB에서는 불가능하다고 판단하는 것도 맞지 않다고 봤다.

### 직접 확인한 내용

- 프로그램이 RTX 4060과 그래픽카드 메모리 8GB를 정상적으로 확인했다.
- 모델 일부를 컴퓨터 메모리로 옮겨 사용하는 방식으로 실제 한 장 생성에 성공했다.
- 컴퓨터 메모리는 도움을 줄 수 있지만 그래픽카드 메모리와 속도까지 완전히 같아지는 것은 아니다.
- 4비트로 줄여 올리는 방법은 가능성을 검토했지만 아직 이 프로젝트에서 직접 시험한 결과는 없다.

### 내가 정한 방향

실제 생성이 되는 현재 방식을 먼저 사용한다. 메모리 부족이 실제로 발생하기 전에는 새로운 줄이기 방법을 추가하지 않는다.

### 지금 설명할 수 있는 내용

가능 여부는 모델 용량만 더해서 판단할 수 없다. 한 번에 그래픽카드에 올라가는 내용과 컴퓨터 메모리로 옮기는 방식을 실제로 시험해야 한다고 설명할 수 있다.

## 6. 이미지 크기와 전신 구도를 분리해서 본 과정

### 막힌 점

전신을 선택했지만 결과에는 다리 일부나 몸의 일부만 크게 나왔다. 세로 크기를 `576×896`으로 바꿔도 전신이 보장되지 않았다.

### 내가 처음 생각한 내용

세로로 긴 이미지를 만들면 전신이 자연스럽게 들어올 것이라고 예상했다. 특정 해상도로 고정하면 문제를 막을 수 있다는 안내도 받았다.

### 직접 확인한 내용

이미지의 세로 길이가 길어도 모델이 인물을 크게 배치하면 머리나 발끝이 잘릴 수 있었다. 해상도 검사는 파일 크기를 정할 뿐, 캐릭터가 화면 안에 들어오는 구도를 보장하지 않았다.

### 내가 정한 방향

- 전신, 상반신과 얼굴 중심을 사용자가 선택한다.
- 전신 결과는 머리와 발끝이 모두 보이는지 사용자가 판단한다.
- 실패하면 새 시드로 다시 생성한다.
- 전신 실패가 계속될 때만 자세와 구도를 확인하는 기능을 검토한다.

### 지금 설명할 수 있는 내용

해상도와 구도는 같은 문제가 아니다. 세로 이미지를 크게 만드는 것과 인물 전신을 화면 안에 배치하는 것은 따로 확인해야 한다고 설명할 수 있다.

## 7. AI의 자동 판정보다 사용자 판단을 먼저 선택한 과정

### 막힌 점

생성된 캐릭터가 기준 이미지와 충분히 비슷한지 프로그램이 자동으로 판단하게 할지, 사용자가 직접 통과시킬지 결정해야 했다.

### 내가 처음 생각한 내용

자동 판정은 편할 수 있지만 실행이 느려질 수 있고, 프로그램의 점수와 내가 실제로 마음에 드는 결과가 다를 수 있다고 생각했다.

### 직접 확인한 내용

현재 목표는 점수가 높은 이미지를 만드는 것이 아니라 내가 사용할 아이콘을 고르는 것이다. 캐릭터의 분위기, 얼굴과 색감은 최종 사용자가 직접 보는 편이 더 분명하다.

### 내가 정한 방향

프로그램은 생성 오류와 이미지 크기 같은 기술적인 사실만 확인한다. 캐릭터 유사성과 사용 가능 여부는 내가 `승인` 또는 `거절`로 결정한다.

### 지금 설명할 수 있는 내용

자동화가 항상 더 좋은 것은 아니다. 판단 기준이 개인의 선호와 직접 연결되면 사용자 선택을 남기는 편이 빠르고 정확할 수 있다고 설명할 수 있다.

## 8. 실패 이미지를 자동 저장하지 않기로 한 과정

### 막힌 점

후보를 만들 때마다 파일로 저장하면 마음에 들지 않는 이미지를 내가 하나씩 찾아서 삭제해야 한다.

### 내가 처음 생각한 내용

이전 후보를 보존하면 비교하기 좋지만, 모든 후보를 파일로 남기는 방식은 정리 작업을 늘린다고 판단했다.

### 직접 확인한 내용

후보는 최대 3장이므로 실행 중 메모리에서 비교할 수 있다. 실제 파일은 내가 승인하고 저장까지 허용한 결과에만 필요하다.

### 내가 정한 방향

- 후보는 자동 저장하지 않는다.
- 실행 중에는 최대 3장을 메모리에 임시로 둔다.
- 후보를 승인한 뒤에도 저장 여부를 한 번 더 확인한다.
- 저장을 허용한 결과만 PNG와 JSON으로 함께 남긴다.
- 저장 실패는 이미지 생성 실패와 구분하고 다시 저장할 수 있게 한다.

### 지금 설명할 수 있는 내용

생성 성공, 사용자 승인과 파일 저장은 같은 상태가 아니다. 이 세 단계를 나누면 실패 이미지를 직접 삭제하는 일을 줄일 수 있다고 설명할 수 있다.

## 9. Git과 GitHub에 올리는 흐름을 직접 확인한 과정

### 막힌 점

처음 커밋을 실행했지만 파일들이 추적하지 않는 파일로 남았고, `git push`는 `Everything up-to-date`라고 표시됐다.

### 내가 처음 생각한 내용

커밋 명령을 실행하면 프로젝트 파일이 바로 GitHub에 올라가는 것으로 생각할 수 있었다. 생성 이미지까지 변경 사항에 나타나는 문제도 있었다.

### 직접 확인한 내용

- 새 파일은 `git add`로 먼저 커밋 대상에 포함해야 했다.
- `git commit`은 내 작업 기록을 만들고, `git push`는 그 기록을 GitHub로 보낸다.
- 생성 이미지와 기준 이미지는 제외 규칙으로 Git 대상에서 뺄 수 있었다.
- 저장소를 공개로 전환하고 문서 변경을 별도 브랜치와 PR로 올렸다.

### 내가 정한 방향

코드와 문서는 GitHub에 올리되 생성 이미지와 기준 이미지는 자동으로 올리지 않는다. 변경은 브랜치, 커밋과 PR 순서로 확인한다.

### 지금 설명할 수 있는 내용

파일 작성, 커밋 대상 등록, 커밋, 푸시와 PR은 서로 다른 단계라고 설명할 수 있다.

## 10. 오류를 바로 고치기 전에 큰 흐름부터 보기로 한 과정

### 막힌 점

생성 파이프라인에서 오류가 보일 때마다 오류가 난 함수부터 바로 수정하면, 화면 코드 안에 비율 계산과 생성 문장 준비가 함께 들어가고 모델 실행 코드가 파일 저장까지 맡을 수 있다.

### 내가 처음 생각한 내용

코드를 작은 함수나 파일로 나누는 것만으로 구조가 정리될 수 있다고 생각할 수 있었다. 하지만 먼저 전체 데이터가 어디서 들어와 어디로 나가는지 정하지 않으면 파일을 나눠도 역할이 다시 섞일 수 있다고 봤다.

### 직접 확인한 내용

- 현재 `gui_main.py`가 화면 처리와 크기·문장·시드 준비를 함께 맡고 있다.
- 현재 `generator.py`가 모델 실행 뒤 이미지와 JSON 저장까지 처리한다.
- 비율 문제와 저장 문제를 같은 생성 흐름에서 다루면 고쳐야 할 위치가 분명하지 않다.

### 내가 정한 방향

GUI 후보 생성 흐름을 사용자 입력, 데이터 가공, AI 모델 실행과 결과 출력의 네 블록으로 먼저 나눈다. 비율, 크기, 생성 문장과 시드 준비는 데이터 가공 블록에서 끝내고 AI 모델 실행 블록은 준비된 요청을 받아 실행만 하도록 한다.

### 지금 설명할 수 있는 내용

하향식으로 구조를 본다는 것은 파일을 먼저 나누는 것이 아니라 전체 흐름의 큰 역할과 경계를 먼저 정하는 일이라고 설명할 수 있다. 오류가 생기면 증상에 따라 어느 블록을 먼저 확인해야 하는지도 구분할 수 있다.

### 아직 확인하지 못한 내용

문서에서 역할을 정한 단계이며 실제 Python 코드는 아직 옮기지 않았다. 구조를 바꾼 뒤에도 기존 이미지 생성이 유지되는지는 구현과 테스트로 확인해야 한다.


## 11. 데이터 이름만 보고 역할을 알 수 있게 정한 과정

### 막힌 점

`UserGenerationRequest`, `PreparedGenerationRequest`와 `GenerationCandidate`처럼 상태나 일반 단어가 앞에 오면 어떤 업무의 데이터인지 이름만 보고 바로 알기 어려웠다.

### 내가 처음 생각한 내용

타입이 있으니 이름은 짧아도 된다고 볼 수 있었다. 하지만 객체를 여러 파일에서 전달하면 이름만 읽고도 무엇을 다루는지 알 수 있어야 구조를 다시 찾는 시간을 줄일 수 있다고 봤다.

### 직접 확인한 내용

- 화면에서 받은 값과 모델이 실행할 값은 서로 포함하는 내용이 다르다.
- 모델이 만든 이미지는 사용자가 승인하기 전까지 최종 결과가 아니다.
- 객체 종류를 이름의 마지막에 두면 입력, 실행 요청과 후보 단계를 구분할 수 있다.

### 내가 정한 방향

객체 이름을 업무 대상, 세부 의미, 객체 종류 순서로 작성한다. 현재 흐름에는 `CharacterGenerationInput`, `CharacterGenerationRequest`와 `CharacterGenerationCandidate`를 사용한다.

### 지금 설명할 수 있는 내용

객체 이름은 길이를 줄이는 것보다 업무 대상과 데이터 단계를 드러내는 것이 중요하다. 마지막 단어를 보면 입력인지, 실행 요청인지, 미승인 후보인지 구분할 수 있다고 설명할 수 있다.

### 아직 확인하지 못한 내용

데이터 이름과 필드를 문서로 정한 단계이며 dataclass와 변환 함수는 아직 구현하지 않았다.


## 현재 내가 설명할 수 있는 범위

현재는 다음 선택의 이유를 내 말로 다시 확인할 수 있다.

- 왜 백엔드가 아니라 로컬 설치형 앱으로 범위를 줄였는가
- 기본 이미지 모델과 기준 이미지 반영 기능의 역할이 어떻게 다른가
- 왜 자세 제어 기능을 아직 추가하지 않았는가
- 컴퓨터 메모리와 그래픽카드 메모리가 어떻게 다르게 사용되는가
- 왜 전신 이미지 크기만 키워서는 잘림 문제가 해결되지 않는가
- 왜 자동 유사도 판정 대신 사용자 승인 방식을 선택했는가
- 왜 생성 후보를 자동으로 파일에 저장하지 않는가
- Git에서 등록, 커밋, 푸시와 PR이 어떻게 이어지는가
- 왜 오류를 바로 수정하기 전에 입력부터 출력까지 네 블록으로 나누는가
- 왜 데이터 객체 이름을 업무 대상·세부 의미·객체 종류 순서로 작성하는가

## 아직 직접 확인해야 하는 내용

다음 내용은 계획하거나 들은 내용일 뿐, 아직 완성됐다고 기록하지 않는다.

- 전신 구도를 안정시키는 최종 방법
- 자세와 관절 확인 기능이 실제로 필요한지 여부

- 다른 Windows PC에 설치하여 실행하는 전체 과정

## 앞으로 기록하는 방법

문제 해결이나 중요한 결정이 끝난 작업에서는 이 문서를 함께 확인한다. 새로 확인된 내용이 있으면 기존 기록을 과장해서 고치지 않고, 새로운 항목을 뒤에 추가한다.

AI가 초안을 정리할 수는 있지만 다음 조건을 지켜야 한다.

- 사용자의 실제 질문, 실행 결과와 확정한 결정만 근거로 사용한다.

- 어려운 표현보다 사용자가 다시 설명할 수 있는 말을 사용한다.

- 사용자의 판단과 AI가 제안한 내용을 섞지 않는다.

## 12. 의상 모델이 오류 없이 틀릴 수 있다는 것을 확인한 과정

### 막힌 점

의상 참고 이미지가 잘렸거나 상의만 있는데 전신 의상으로 선택한 경우, 모델이 오류를 알려줄 것인지 알 수 없었다. 목표가 뒷모습인데 의상 뒷면이 없는 경우도 같은 문제가 생길 수 있다고 봤다.

### 직접 확인한 내용

- 공식 상의 이미지와 사람 이미지 생성은 정상적으로 끝났다.
- 같은 상의를 전신 의상으로 잘못 지정해도 오류 없이 이미지가 생성됐다.
- 의상의 오른쪽 일부를 잘라 입력해도 오류 없이 이미지가 생성됐다.
- 최종 보호 합성은 의상 허용 영역 밖의 픽셀을 바꾸지 않았다.

### 내가 정한 방향

모델이 실행됐다는 사실과 의상 참고가 충분하다는 판단을 구분한다. 의상 종류, 전체 노출 여부와 앞면·뒷면 정보는 생성 전에 확인해야 한다. 없는 뒷면을 모델이 추측한 결과를 원본 의상 유지 성공으로 판단하지 않는다.

### 지금 설명할 수 있는 내용

생성형 AI는 입력 정보가 부족할 때 항상 오류를 내는 것이 아니라 빈 부분을 추측해서 채울 수 있다. 그래서 기술적인 실행 성공과 사용자가 원하는 의상 재현 성공은 별도의 결과라고 설명할 수 있다.

### 아직 확인하지 못한 내용

애니 캐릭터 의상 이미지에서 전체 노출과 앞면·뒷면을 자동으로 얼마나 정확히 구분할 수 있는지는 확인하지 않았다. 자동 판정보다 사용자 확인이 먼저 필요한지 다음 입력 정책에서 정해야 한다.
