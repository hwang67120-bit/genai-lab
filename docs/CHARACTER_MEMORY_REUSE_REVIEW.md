# 캐릭터 기억 재사용 가설(H1) 검토와 최소 시험 설계 (2026-10-22, Claude, 초안)

> 범위: 설계·시험 요청서까지. 코드 수정·GPU·내려받기·커밋은 하지 않았다. CPU로 한 계산 1건(§1 B0)만 실제로 돌렸다.
> 시험 요청서: `outputs/generalization-20261012/codex_gpu_request_33.md`(초안, 승인 전).
> 10/13 사례 검색 검토(`docs/RAG_FEASIBILITY_REVIEW.md`)는 '지금 실패를 고치는가'만 봤다. 이 문서는 같은 질문을 제품 쪽에서 다시 본다. 같은 캐릭터를 다시 쓸 때 사람 일이 줄고 동일성이 나아지는가.

## 10/22 보완 요약(사용자 지시: B는 구현, C는 설계 보완만, GPU 미승인)

- **B(캐릭터 ID 조회)는 구현했다(⑧).** 세 커밋은 따로 되돌릴 수 있다: 저장 모듈, 확인 창 연결, 관리 도구.
  - 기존 파일 경로 기록은 지우지 않고 처음 등록할 때 가져온다.
  - 같은 캐릭터 연결은 사람이 고르고 체크해야만 된다. 잘못 연결하면 확인 창이나 관리 도구로 해제한다.
  - 기억에는 성별·부위·특징표만 있어서 새 의상·요청을 덮어쓸 자리가 없다.
- **C(승인 머리 참조)는 참조 4개를 고정했다(⑨).** 고정 내용은 `outputs/generalization-20261012/memory-ref-33/manifest.json`의 크롭·마스크·흰 배경·SHA다.
- **눈으로 확인하니 C의 근거가 약해졌다.**
  - M3 승인 결과에도 원본처럼 손이 이마를 가린다. 'M3는 손 없는 두 번째 시점을 준다'는 가설 G2가 틀렸다.
  - M6 승인본은 원본보다 머리가 어둡고 진하다.
  - 승인 크롭이 주는 새 정보는 '같은 모델이 장면 속에서 통과 판정을 받은 모습' 하나다. 원본보다 정확한 색·형태 정보는 아니다.
  - 그래서 GPU 시험은 **'개선 확인'보다 '퇴행·따라옴이 없는지와 비용' 확인**에 가깝다. 실행 여부는 사용자 결정이다.
- **8단계는 제품 설정과 다르다.** 차이는 CFG 1.0, 가속 LoRA, 재시도 없음이다. 그래서 8단계 결과로는 **개선을 주장하지 않는다.** 해석 범위는 ⑨-3에 고정했다.
- **메모리 상한 6.5GiB는 유지한다.** 자동으로 완화하지 않는다. 램 48GB 증설은 GPU(8GB) 여유가 아니다.

## 결론

1. **H1은 두 가지로 나뉜다. 하나(B)는 이미 대부분 구현돼 있고, 다른 하나(C)는 지금 계약상 불가능한 새 기능이다.**
   - **B: 확정 특징 재사용.** 이미 있다. 특징표는 확인 창에서 한 번 확정하면 다음에 미리 채워지고 생성 문장에 들어간다(D-120). 시험에서 넣는 특징표도 저장된 값과 같다. 따라서 **B를 GPU 시험군으로 만들지 않는다.**
   - 빈틈은 하나다. 저장 열쇠가 **파일 경로**라서 같은 캐릭터라도 다른 파일(승인 결과·편집 승인본·다시 저장한 그림)을 열면 저장값을 못 찾는다.
   - **C: 승인 그림을 시각 참조로 재사용.** 지금 모델에 들어가는 그림은 '기준 그림 + 같은 그림의 머리 크롭 (+ 골격)'뿐이다. 다른 그림을 참조로 넣는 것은 검증 코드가 막는다(`qwen_free_generation.py:76`). **H1에서 생성 품질을 바꿀 수 있는 것은 C뿐이다.**
2. **같은 캐릭터 조회는 일반 저장·조회(캐릭터 ID + 이미지 SHA 색인)로 충분하다.** 벡터 검색·RAG는 필요 없다. 비슷한 캐릭터를 찾는 일은 H2의 몫이며 이번 범위 밖이다.
3. **최소 시험: 4명 6줄 × 2군(A 현재 / C 추가) = 12장, 8단계.**
   - 예상 시간은 약 2시간 반이다. 교체(C-replace)는 10/22 보완에서 뺐다(⑨ 9-2).
   - 판정은 사용자 블라인드 2장 비교 6묶음이다.
   - 통과 기준과 중대 퇴행 정의는 §6에 시험 전에 고정했다.
4. **확인된 사실 하나(B0, CPU):** 승인 결과 그림을 새 기준으로 열면 자동 추정이 사용자 확정값과 **캐릭터당 0~4칸, 평균 약 2칸** 다르다.
   - M6 승인 결과는 파란 머리(`blue_hair`)를 `grey_hair`로 잘못 채운다.
   - 이것이 B(ID 조회)가 줄일 수 있는 수동 작업이다. 생성 품질과는 관계없다.

### 원인 가설
- **G1:** 사람 손이 가는 곳은 ① 입력 단계(다른 파일이면 특징 다시 확인), ② 결과 단계(판정·재시도·보정본 고르기), ③ 규칙 수정이다. **B는 ①만 줄인다.** ②·③을 줄이려면 생성 결과가 실제로 좋아져야 한다. 그 후보가 C다.
- **G2(C의 근거):** M3·M6의 머리색 실패는 원본 그림 자체의 방해와 관계있을 수 있다.
  - M3: 손이 이마 위 머리를 가린다.
  - M6: 어두운 배경과 푸른 테두리 빛.
  - 요청 32에서 배경을 흰색으로 바꿔도 낫지 않았다(D-146). 그래서 '배경'보다 '머리 크롭에 담긴 색 정보'가 문제일 수 있다.
  - 사용자가 통과시킨 결과(M3 공원, M6 자동 보정본)는 같은 캐릭터를 방해 없이 보여 주는 두 번째 시점이다.

### 아직 검증하지 않은 기대 효과
- C가 머리색·얼굴 유지를 개선한다.
- 위험도 있다. 승인 그림은 모델이 만든 복사본이다. 원본보다 정보가 적고, 모델 자신의 그림 버릇이 쌓일 수 있다('복사의 복사').
- 이전 장면의 조명·자세가 따라올 수 있다.

| 승인 결과·항목별 판정 | 실행 폴더 `judgement.json`(D-114). 통과는 체크 5개뿐, 실패만 `failure_type`. 시험 판정은 `ledger.json`. 캐릭터 단위 색인 없음 | 캐릭터 기억에 승인 그림(SHA)·승인 범위·당시 연출·모델 설정·항목별 판정을 연결 | 연결이 새것(기록 자체는 있음) |

## ③ 저장 · 조회 · 선택 · 생성 · 판정 흐름

### 저장 구조(캐릭터 하나 = 파일 하나, `character-memory/<character_id>.json`)

```
schema: character_memory/1
character_id: 처음 확정할 때 만드는 UUID(사람이 이름을 붙일 수 있음)
canonical: {path, sha256, size:[w,h], origin:"user_upload", registered_at}      # 기준 원본. 자동으로 바뀌지 않는다
images: [{sha256, path, role: canonical | approved_free | approved_edit, parent_sha256,
          run, trace, attempt, variant, size:[w,h]}]                             # SHA로 찾는다(경로는 참고용)
features: {항목: {value, source: tags|pixels|user, confidence(태그 점수·픽셀 수),
                  evidence_image_sha256, confirmed_by_user, confirmed_at}}       # 항목 = 머리 길이·모양·색, 눈 색, 머리 장식, 피부, 고유 형태
parts: {ears|tail|wings: present|absent|unknown, count|null, evidence_image_sha256, confirmed_by_user}
regions: [{image_sha256, kind: head_crop|parts_npz, box|path, coordinate_basis:"768x1024 canvas of that image"}]
approvals: [{image_sha256, mode: free_generation|outfit_edit, approved_at, steps, reviewer:"user",
             scope: {identity_checked:true, items_judged:{hair_color, face_hairstyle, skin, outfit, parts}},  # 판정 항목만 '확인됨'
             staging: {request_text, pose_key, background_words, lighting_note},
             outfit: canonical | garment_sha256,
             model: {name, gguf_sha256, steps, true_cfg, accelerator}, code_sha256, judgement_ref}]
failures: [{run, case, failure_type(TAXONOMY), items, applied: retry|hair_restored|hair_auto|rule(D-xxx), outcome}]
```

- **좌표·마스크는 그 그림의 크기·좌표계와 함께만 저장한다.** 다른 그림·새 자세 결과에 옮겨 쓰지 않는다. 결과 분할은 결과에서 다시 찾는다(지금 `observe_result`와 같은 원칙).
- **생성 결과는 자동 승인하지 않고 canonical을 대체하지 않는다.** 사람이 승인해 내보낸 그림만 `approved_*`로 등록한다. 8단계 미리보기 승인은 `steps:8`로 남기고 참조 후보에서 뺀다.
- 기존 QSettings 저장은 그대로 둔다. 기억 파일이 없으면 지금처럼 동작한다.

### 이번 요청에서 특징마다 정하는 역할(기억에 저장하지 않고 실행 trace에 남김)

| 역할 | 정하는 방법(기존 코드 재사용) | 자유 생성 예 | 의상 편집 예 |
|---|---|---|---|
| ① 캐릭터 고유 특징 | 확정 특징표·부위 | 머리·눈·피부·장식·부위 | 같음 |
| ② 이번에 유지할 상태 | ① 중 요청이 가리지 않는 것 + 계약상 유지 대상 | ① + **의상** | ① |
| ③ 사용자가 바꿀 대상 | 계약 | 자세·구도·배경 | **의상** |
| ④ 확인할 수 없는 항목 | 모름/약함 + `request_conflicts` | 눈 감기면 눈 색 등 | 같음 |

### 조회 · 선택 · 생성 · 판정

1. **조회(정확 일치만):** 입력 그림 SHA → `images` 색인 → character_id.
   - 못 찾으면 확인 창에서 사용자가 '저장된 캐릭터 고르기'를 할 수 있다. 사람이 명시적으로 고르는 것이다.
   - 그래도 없으면 **지금 경로 그대로**(태그 미리 채움, 참조 추가 없음).
   - 비슷해 보이는 다른 캐릭터를 자동으로 고르지 않는다.
2. **특징 선택:** 확정 특징 중 ④를 뺀 것을 쓴다(지금 `features_sentence`와 같음).
   - 기억의 확정값은 입력 확인 창 **미리 채움**으로만 들어간다. 사람이 확인해야 생성 조건이 된다.
3. **참조 선택(결정적 규칙, 시험 전 고정).** 같은 character_id의 `approvals` 중에서 고른다.
   - R-a: 사용자 승인, quality_pass, **40단계**, 차단 아님.
   - R-b: **지금 요청과 장면이 다름**(자세 키·배경 낱말이 겹치지 않음). 같은 장면 복사를 막고, 기억에 없는 장면에서 효과를 본다.
   - R-c: 그 그림에서 얼굴이 보임(자기 분할의 `head_box`가 `derived_head_crop`·`head` 범위). 그 장면이 눈 감기·뒷모습이 아님.
   - R-d: 기준 원본 대비 색 충실도가 가장 높은 것. 머리 띠별 오차(`hair_auto_restore.band_error`)와 피부 ΔE의 합이 가장 작은 것을 고른다. 같으면 먼저 승인한 것.
   - 고른 것과 **제외한 것·제외 이유**를 `trace.input_facts.memory_selection`에 남긴다.
4. **참조 모양 = 승인 그림의 머리 크롭.** 그 그림 자기 분할로 자르고, 머리 밖 픽셀은 흰색으로 칠한다. 이미지 전체를 쓰지 않는 이유:
   - 전체 그림에는 이전 자세·배경·조명이 그대로 있어 **따라오기 쉽다**(가장 큰 위험).
   - 문장 처리 쪽 입력은 그림마다 약 384²로 줄어든다. 전신 그림에서는 얼굴이 아주 작아져 동일성 정보가 적다.
   - 지금 계약도 동일성은 머리 크롭으로 전한다(D-123). 같은 통로를 하나 더 쓰는 것이다.
   - 한계: 머리 둘레 조명(밤 장면의 푸른 기운)은 크롭에도 남는다. 그래서 R-d로 색 충실도를 거른다.
5. **생성:** 입력 그림을 둘 중 하나로 구성한다. 둘을 한 시험에서 섞지 않는다.
   - C-add: [기준 캔버스, 기준 머리 크롭, **승인 머리 크롭**] 3장.
   - C-replace: [기준 캔버스, **승인 머리 크롭**] 2장. (10/22 보완에서 제외 — 원본 기준을 잃음, ⑨ 9-2)
   - 승인 그림 SHA를 기억 기록과 대조한 뒤에만 넣는다.
6. **판정:** 지금 결과 확인 창과 판정 형식 그대로. 판정 항목에 '이전 참조에서 따라온 것(없음/자세/배경/조명/의상)'을 추가한다. 승인되면 기억에 등록한다(사람 승인 뒤에만).

## ⑥ 통과 · 퇴행 · 중단 기준 (시험 전에 고정)

**판정 항목(줄마다 두 결과를 가린 채로):**
- 종합 통과/실패, 실패 분류(`free_generation_metrics.TAXONOMY`)
- 머리색(색조·밝기·분포: 같음/다름), 얼굴·헤어스타일, 피부(같음/조명 탓 차이/다름)
- 의상·장식, 귀·꼬리 존재·개수, 요청 자세·장면 반영
- **이전 참조에서 따라온 것(없음/자세/배경/조명/의상)**
- 두 결과 비교(동일성: X가 나음/같음/Y가 나음)

자동 측정(머리 띠별 오차·피부 ΔE·태그)은 보조 기록이다. **확신 낮음·측정 불가는 성공으로 세지 않는다.**

**40단계 확인으로 넘어가는 조건(모두 충족):**
1. 알려진 실패 2줄(M3-S2·M6-S4)에서 **1줄 이상 개선**이다. 개선 = A 실패 → C 통과, 또는 둘 다 실패지만 머리색 항목에서 C가 '나음'. **'나쁨'은 0줄.**
2. 나머지 4줄에서 A 통과 → C 실패가 0줄이고, 동일성 비교 'A가 나음'도 0줄.
3. '따라옴'이 0줄.
4. 요청 반영: A는 따랐는데 C는 안 따른 줄이 0.
5. 메모리 상한 초과·중단 0. 시간 증가는 기록만 한다.

**중대 퇴행(하나라도 있으면 C-add 채택 불가, 원인 기록):**
- 얼굴·헤어스타일이 다른 캐릭터처럼 바뀜
- 새 부위·개수 변화
- 안전 차단
- 참조의 자세·배경·조명이 새 결과에 나타남
- 정상 캐릭터(N1·K)에서 통과 → 실패

**즉시 중단:**
- `memory_stopped` 또는 reserved > 6.5GiB → C-add 중단, 기록만
- 기억 참조 SHA 불일치
- 처음 3줄 가운데 2줄 이상 '따라옴'

**재현성:** A의 M3-S2가 요청 32와 픽셀이 다르면 비교를 멈추고 원인부터 본다.

**보고할 수치:**
- 품질: 첫 시도 통과(A vs C)
- 비용: 줄당 시간·최고 메모리
- 사람 작업: 최초 등록 비용 + 요청당 추가 작업. **등록 비용을 빼고 '수동 작업이 줄었다'고 쓰지 않는다**
- B0 칸 수 감소(구현 뒤 CPU)

| 결과 | 결정 |
|---|---|
| C-add가 통과 기준 미달, B0 효과만 확인 | **B(캐릭터 ID 조회·승인본 연결)만 채택.** 단순 저장·조회, 생성 조건 불변. C는 보류. 사례 수만 늘리지 않는다 |

| 어느 경우든 | 같은 캐릭터 결과를 **처음 보는 캐릭터 효과(H2)로 확대 해석하지 않는다** |

**H2(처음 보는 캐릭터에 비슷한 사례의 처리 방법 재사용)는 H1 결과 뒤 별도로 설계한다.**
- 재사용 대상은 다른 캐릭터의 외형이 아니라 **처리 방법**이다. 예: '옅은 중간색 머리 + 어두운 배경이면 자동 보정 문턱 확인'.
- 근거 자료는 기억의 `failures`(실패 분류 + 적용 처리 + 결과)다.

**기억 위치:**

- 시험은 자기 임시 폴더만 쓴다(conftest).

**기존 파일 경로 기록의 연결·이관:**
- QSettings 경로 기록은 그대로 둔다. 기억 기능을 되돌려도 지금처럼 동작한다.

- 한계: 경로 기록의 열쇠는 경로 문자열이다. 같은 파일도 `Z:\`와 `\\192.168.0.109\`는 다른 기록이다.

**같은 캐릭터 연결을 사람이 확인하는 방법:**
- 연결 안 된 그림의 기본값은 '새 캐릭터로 등록'이다. 다른 저장 캐릭터에 잇는 것은 사람이 그 캐릭터를 고르고 기준 그림 썸네일을 본 뒤 **"이 그림은 위 캐릭터와 같은 캐릭터입니다"를 체크해야** 시작 버튼이 켜진다.
- 예전 자유 생성 승인 저장본(`.review.json`이 가리키는 기준 그림이 이미 등록된 경우)은 **제안**으로만 보인다. 체크가 필요하다.
- 편집 승인본의 예전 기록에는 원래 캐릭터 SHA가 없어서 제안하지 않는다. 직접 골라야 한다.
- 승인 저장 등록은 같은 그림의 사람 승인 기록(`reviewer: user`, '같은 캐릭터' 체크, SHA 일치)이 있을 때만 한다. 8단계 미리보기 승인은 `steps: 8`로 남겨 나중에 참조 후보에서 뺄 수 있게 한다.
- 비슷해 보이는 캐릭터를 자동으로 찾거나 잇지 않는다.

**잘못 연결했을 때 해제:**
- 확인 창: 연결된 그림이면 '연결 해제 — 새 캐릭터로 등록' 또는 '연결 해제 — 연결 없이 이번만 사용'을 고를 수 있다.
- 관리 도구: `unlink <ID> <그림> --reason`.
- 해제 기록(`unlinked`)과 로그를 남긴다. 기준 원본은 해제할 수 없고, 캐릭터 삭제(`remove`, 되돌릴 수 있음)를 쓴다.
- 확정 특징을 잘못 고친 경우를 위해 이전 정체성 10개를 `identity_history`에 남긴다.

**새 의상·요청을 과거 값으로 덮어쓰지 않는 장치:**
1. 기억에는 성별·부위·특징표만 들어간다. 다른 키는 저장 함수가 거부한다(시험 있음).
2. 연결 줄은 성별 콤보·부위 체크·특징표 글 상자만 채운다. 요청 문장·기준 종류·빠른 미리보기·입힐 옷은 건드리지 않는다(시험 있음).
3. 사람이 이미 고친 칸은 연결 대상을 바꿔도 다시 채우지 않는다(시험 있음).
4. 기억의 값은 미리 채움일 뿐이다. 생성 조건은 지금처럼 확인 창에서 사람이 확정한 값이다.

**시험:**
- 새 시험 18개: 저장 모듈 10, 확인 창·작업실 6, 관리 도구 2.
- 기존 확인 창·편집·자유 생성 시험 포함 관련 41개 통과. 전체 결과는 커밋 기록에 적는다.
- GPU·실제 생성은 하지 않았다.

### 9-1. 선택한 승인 머리 참조가 현재 입력에 없는 어떤 정보를 주는가 (원본 크롭과 나란히 보고 적음)

| 캐릭터 | 고른 참조 | 지금 입력(원본 머리 크롭)에 없는 것 | 오히려 다른 것(위험) |
|---|---|---|---|
| M3 | S3 눈길 raw | 두 눈을 다 뜬 얼굴(원본은 한쪽 윙크), 어두운 배경 테두리 빛이 없는 머리 | **손이 이마를 가리는 것은 그대로**(모델이 원본 손 자세를 옮김). 눈이 원본보다 진한 파랑 |
| M6 | S3 자동 보정본 | 어두운 배경 없음, 정면에 가까운 얼굴 | **머리가 원본보다 어둡고 진한 남색**(밤 장면 + 보정), 눈이 진한 파랑 |
| N1 | S1 공원 raw | 손이 얼굴 옆에 없는 머리(원본은 V자 손) | 눈 분홍이 더 진함, 뿔·머리띠 세부는 모델식 |
| K | S1 공원 raw | 거의 없음(같은 정면) | 오드아이가 원본보다 훨씬 진함(파랑/빨강), 리본 모양 다름 |

- **결론:** 승인 크롭은 원본보다 정확한 색·형태 정보를 주지 않는다. 새 정보는 '가림·배경 방해가 적은 다른 시점'(M3 눈, M6 배경, N1 손)과 '이 모델이 장면 안에서 통과 판정을 받은 모습' 정도다.
- 색은 오히려 모델 쪽으로 진해져 있다(4명 모두 눈 채도 상승). 그래서 C-add가 동일성을 **원본보다 모델 해석 쪽으로 끌 위험**이 있다.
- 시험하면 확인할 것은 이 위험(퇴행)이 주가 된다.
- 크기: 승인 크롭 151~297px, 원본 크롭 150~270px로 비슷하다. 둘 다 모델 안에서 조건 그림마다 약 1024² 면적으로 커지고(diffusers `VAE_IMAGE_SIZE`), 문장 처리 입력은 384²다. 해상도로 더하는 정보는 없다.

### 9-2. 원본 머리 대신 승인 결과를 고른 이유와 승인 범위

- **C-add는 원본 머리를 대신하지 않는다.** image 1(원본 캔버스)과 image 2(원본 머리 크롭)는 그대로 두고 image 3을 **더한다**. 원본은 계속 최상위 기준이다.
- 원본을 승인 결과로 **바꾸는 것**(C-replace)은 이번 설계에서 뺐다. 9-1에서 승인 크롭이 원본보다 나은 정보를 주지 않는 것을 확인했으므로, 원본을 빼면 동일성 기준을 잃는다.
- 승인 결과를 더 넣어 보는 이유는 하나다. 장면 조명 아래 같은 캐릭터가 통과한 실제 예를 보여 주면, 모델이 장면에서 색을 덜 바꿀 수 있다는 가설이다(미검증, 근거 약함).
- **승인 범위**: 요청 29의 사용자 판정은 '종합 통과(같은 캐릭터·같은 의상·요청 반영·심한 이상 없음·완성도)'다.
  - 판정은 **전신 그림 크기에서 묶음(4~6장) 보기**로 했다. 머리 확대 크기에서 색·눈·장식을 따로 판정하지 않았다.
  - 사용자 기준상 작은 머리 장식은 중요도가 낮다(D-143). 그래서 승인은 "머리 크롭이 원본과 같다"를 보장하지 않는다(9-1의 눈 채도 차이).
  - M6 참조는 머리색 자동 보정본(후처리 그림)이다. 승인 범위에 '보정된 색'이 포함되지만 모델이 직접 그린 그림은 아니다.

### 9-3. 8단계 설정과 제품 설정의 차이와 해석 범위

| 항목 | 제품(최종) | 8단계 미리보기 | 결과 해석에 미치는 영향 |
|---|---|---|---|

**해석 범위(시험 전 고정):**
- (a) 8단계에서 **따라옴·중대 퇴행·메모리 초과**가 나오면 C-add를 중단한다. 이런 강한 신호는 40단계에서도 날 가능성이 크다고 보지만, 그것도 '중단' 근거로만 쓴다.
- (b) 8단계에서 **개선**이 보이면 그것만으로 채택·개선을 주장하지 않는다. 40단계 확인 요청으로만 이어진다.
- (c) 8단계에서 **차이 없음**이면 색 항목은 결론을 내지 않는다(8단계가 색에 약함). 이때는 C를 보류하고, 40단계 확인은 사용자가 따로 결정한다. 자동으로 진행하지 않는다.
- (d) 어떤 경우에도 8단계 결과를 40단계 운영 집계(요청 29 기준선)와 합치지 않는다.
