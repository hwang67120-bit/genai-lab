## 1. 목적과 착수 순서

사용자가 기다리는 시간을 줄이면서 RAM과 VRAM의 사용량을 지원 환경 안에서 관리한다. 이미지 품질과 기존 입력 확인·승인·실패·취소 동작을 유지하는 것이 전제다. 메모리 사용량을 무조건 낮추거나 특정 언어로 옮기는 것이 목적은 아니다.

전체 프로젝트 순서는 **동일성 계획 종료 → 학습 → 메모리 최적화 → 배포 호환성 → 연동 호환성**이다. 이 계획은 메모리 최적화 단계의 준비 문서이며 앞 단계를 건너뛰어 실행하는 승인이 아니다. 실제 착수 시 학습이 반영된 모델과 코드로 기준을 다시 고정한다. 현재 로드맵은 [ROADMAP.md](ROADMAP.md)를 따른다.

최적화는 두 우선순위로 나눈다.

| 구분 | 범위 | 착수 조건 |
|---|---|---|
| 1순위 | Python 로직과 기존 라이브러리 호출을 조정해 반복 계산·복사·적재를 줄인다. | 단계별 기준 측정을 확보한 뒤 작은 변경부터 비교한다. |
| 2순위 | 1순위 이후에도 남고 기존 실행 방식으로 해결하기 어려운 병목에 대해 네이티브 구현·실행 엔진을 검토한다. Rust를 우선 실험 언어로 둔다. | 병목의 위치·비중·기존 도구의 제한이 측정으로 확인돼야 한다. |

현재 **다른 언어가 반드시 필요한 것으로 확정된 항목은 0건**이다. Rust 조사·학습과 제품 채택은 별도 판단이다. 1순위만으로 목표를 충족하면 제품에 Rust를 추가하지 않아도 된다.

## 3. 판단에 사용하는 기초 이론

| 이론 | 현재 프로젝트에 적용하는 방법 | 피해야 할 해석 |
|---|---|---|
| 시간적 지역성 | 4장에서 반복 쓰는 프롬프트·얼굴 특징을 요청 안에서 재사용한다. | 사용 빈도와 크기를 보지 않고 모든 결과를 무기한 보관한다. |
| 공간적 지역성 | 배열의 배치·순회 순서와 필요한 처리 영역을 확인한다. 크롭 주변만 처리해 작업 집합과 읽기·쓰기를 줄인다. | Rust나 연속 배열이라는 이유만으로 캐시 효율이 좋아졌다고 단정한다. |
| 메모리 계층과 대역폭 | 저장장치·RAM·VRAM 각각의 점유와 이동량을 구분한다. | RAM 여유를 VRAM 여유로 간주하거나 전송량을 보지 않고 모델을 옮긴다. |
| 암달의 법칙 | 전체 시간 중 개선 대상의 비율로 최대 효과를 계산한다. | 작은 준비 계산을 줄인 비율을 전체 생성 속도 개선으로 보고한다. |
| 워크로드 분류 | 계산, 메모리 접근, 파일 입출력, 장치 전송, 동기화 대기를 구분한다. | Python 프로세스에서 발생한 시간을 모두 인터프리터 비용으로 분류한다. |
| 메모리 할당자 | 활성 텐서, 재사용을 위한 예약 영역, 단편화, 실제 누수를 구분한다. | reserved가 높다는 이유만으로 누수라 하거나 매번 캐시를 비운다. |

전체 시간에서 개선 대상의 비중이 p이고 그 부분이 s배 빨라지면, 단순 직렬 모델에서 전체 속도 향상은 1 / ((1-p) + p/s)이다. 예를 들어 비중이 10%인 구간을 완전히 제거해도 전체 시간 감소 상한은 10%다. 이는 설명용 예시이며 현재 프로젝트의 측정 비중이 아니다. 연산·전송이 겹치는 경우 단순 합산 대신 실행 구간의 겹침을 확인한다.

계산 결과를 캐시하는 것과 CPU/GPU 하드웨어 캐시, PyTorch 메모리 풀은 서로 다르다. Rust의 소유권 해제도 Python·외부 라이브러리·GPU 할당 전체를 즉시 반환한다는 뜻은 아니다.

## 4. 기준 측정 계획

### 4.1 사용자 시나리오

| 시나리오 | 확인 목적 |
|---|---|
| 앱 시작 후 첫 요청 | 프로세스 시작·모델 적재를 포함한 최초 대기 시간 |
| 같은 캐릭터·같은 의상으로 다음 요청 | 분석·특징·모델 재사용 효과 |
| 캐릭터는 같고 의상만 변경 | 캐릭터 분석만 안전하게 재사용하는지 |
| 캐릭터·의상 모두 변경 | 오래된 결과를 잘못 재사용하지 않는지 |
| 취소·오류 후 다음 요청 | 참조·모델·임시 버퍼가 남거나 다음 요청을 오염시키는지 |
| 연속 요청 | 활성 메모리의 누적 증가와 캐시 상한 준수 |
| 별도 Qwen 실행으로 전환 | 기본 생성 자원을 해제한 뒤 편집이 시작되는지. 편집 시험은 별도 승인 범위다. |

앱 재시작 상태, 운영체제 파일 캐시 상태, 모델 상주 상태를 따로 기록한다. 앱을 재시작했다는 이유만으로 디스크 캐시까지 비어 있다고 표기하지 않는다.

### 4.2 구간별 기록

1. 입력 읽기·스냅샷·디코딩
2. 분석 프로세스 시작과 모델 적재
3. DWPose·머리 검출·전경 분리·태깅 각각의 추론
4. 얼굴 크롭·마스크·프롬프트 조립
5. 생성 모델 적재
6. 텍스트·얼굴 참조 인코딩과 어댑터 특징 계산
7. 반복 추론·VAE 디코딩
8. 원시 이미지·기록 저장, 화면 전달, 사용자 승인 후 내보내기

사용자 확인 대기는 별도 기록한다. 모델 적재와 인코딩을 포함한 전체 경과 시간도 함께 보관한다. GPU의 비동기 실행을 고려해 측정 범위를 명확히 하고, 세밀한 측정용 동기화·프로파일러가 실제 실행을 늦출 수 있으므로 일반 실행 시간과 구분한다.

### 4.3 메모리와 실행 조건

- 부모·분석 자식·생성 프로세스별 RAM 사용량과 동시에 살아 있는 프로세스를 기록한다. 공유 페이지를 단순 합산한 값을 실제 물리 RAM 총량으로 주장하지 않는다.
- PyTorch allocated/reserved 피크, GPU 전용·공유 메모리, 가능하면 장치 전송량·시간을 구분한다.
- 단계 종료 후와 다음 요청 시작 전 사용량을 기록한다. reserved가 유지되는 것과 활성 텐서가 계속 늘어나는 것을 구분한다.
- 모델·패키지·드라이버·장치·입력 SHA·설정·seed·실행 순서·다른 GPU 작업 유무를 고정하거나 기록한다.
- 비교 횟수·총 생성 상한·자원 중단 조건은 실행 전 승인된 검증 계획에 적는다. 이번 문서가 추가 생성이나 설치를 승인하지 않는다.
- 반복 측정에서 중앙값·범위와 최초 실행 값을 함께 제시한다. 절감률·목표 시간은 기준 측정 전 임의로 정하지 않는다.

반복 동작은 정적으로 확인했다. 아래 순서는 조사·작은 변경의 우선순위이며 절감량 순위가 아니다. 각 항목은 독립 변경으로 검증한다.

### 모델 상주·할당자 정책은 별도 검토

현재 생성 모델은 후보마다 다시 적재하지 않는다. 요청당 한 번 적재해 4장 동안 공유하고 요청 종료 시 해제한다. 태거도 한 분석 요청 안에서는 캐릭터·의상에 같은 세션을 쓴다. 이 동작을 중복 적재 결함으로 기록하지 않는다.

다음 요청까지 모델을 유지하거나 CPU 분석 프로세스를 상주시킬 수는 있지만, 재적재 시간 감소와 RAM/VRAM 점유 증가를 함께 비교해야 한다. 먼저 작은 분석 결과와 임베딩을 캐시하고, 모델 상주는 실제 재요청 패턴과 메모리 예산을 확인한 뒤 결정한다. Qwen 전환 시 기존 해제 계약을 유지한다.

empty_cache()를 반복 추가하거나 할당자를 교체하는 작업은 현재 우선 항목이 아니다. 단편화·누수의 증거 없이 reserved 값을 낮추는 것만을 성과로 삼지 않는다.

### 캐시 설계 조건

- 요청 내부 캐시부터 시작하고 요청 종료·취소·실패 시 수명을 끝낸다.
- 요청 간 캐시는 항목 수·총 바이트·퇴출 정책을 정한다. 무제한 전역 캐시는 사용하지 않는다.
- 키에는 입력 내용 SHA, 전처리·모델 revision/가중치 해시, 설정, 자료형 등 결과를 바꾸는 조건을 포함한다.
- 분석 캐시는 원시 분석 근거를 재사용한다. 성별·의상·꼬리 문구 등 현재 사용자 승인은 별도로 적용한다. 이전 승인을 자동으로 재사용하지 않는다.
- 읽기 전용 공유를 기본으로 검토한다. 라이브러리가 입력을 수정하면 해당 경계에서 필요한 복사를 유지한다.
- 검증된 스냅샷은 재사용해도 되지만 승인 이미지 무결성 확인을 삭제하지 않는다.
- seed별 노이즈·스케줄러 상태·생성 중간 결과는 공통 데이터로 재사용하지 않는다.

## 6. 2순위 — 남은 병목과 Rust 실험

### 6.1 진입 조건

다음 기록이 있어야 2순위 제품 실험을 시작한다.

1. 1순위 적용 후 동일 조건의 기준 시간·메모리가 있다.
2. 남은 병목 함수·연산·전송 구간과 전체 시간 비중을 설명할 수 있다.
3. 기존 NumPy·Pillow·PyTorch·ONNX Runtime 등으로 해결하지 못한 이유가 있다. 이미 네이티브로 실행되는 연산을 단순히 Rust로 다시 작성하는 것은 개선 근거가 아니다.
4. 작은 입력/출력 계약과 오류·취소·소유권 경계를 정의할 수 있다.
5. 추가 환경·패키지·GPU 실행이 필요하면 별도로 승인받는다.

| 조사 대상 | 가능한 대응 | 현재 상태 |
|---|---|---|
| 남은 CPU 배열 연산 | 기존 Rust 라이브러리 조합 또는 작은 확장 함수 | 병목 미확정 |
| GPU 연산 내부 | 기존 최적화 연산·실행 엔진·커널 검토 | Rust 사용 자체로 해결되는 범위가 아님 |
| RAM↔VRAM 전송 | 전송량·빈도·동시 실행·모델 배치 검토 | Python 제어로 개선 가능한 부분을 먼저 분리 |
| 메모리 용량 부족 | 작업 집합·모델 구조·정밀도·해상도 등 검토 | 품질·출력 계약이 바뀌는 선택은 별도 결정 |
| 하드웨어 대역폭 한계 | 전송량 감소 또는 지원 사양 검토 | 언어 교체로 물리 대역폭이 증가하지 않음 |

Qwen 편집 최적화는 위 원칙을 적용하되 별도 시험으로 다룬다. 현재 긴 편집 시간을 Rust 도입 근거로 바로 사용하지 않는다.

### 6.3 실험과 제품 채택

작은 함수 하나를 대상으로 최적화된 Python 기준 구현과 Rust 구현을 비교한다. 같은 입력에서 결과·오류 동작을 확인하고, 함수 단독 시간과 앱 전체 시간·최대 RAM을 각각 기록한다.

측정 변동을 넘는 실질적인 이득과 배포·유지보수 비용을 함께 검토한다. 효과가 작거나 연결 비용으로 사라지면 제품에 넣지 않고 실험 결과로 남긴다. 학습용 실험이 성공했다는 이유만으로 운영 채택하지 않는다.

## 7. 검증과 완료 조건

- 이번 단계에서는 프롬프트·seed·해상도·단계·모델·생성 의미를 바꾸지 않는 최적화를 우선한다.

- 해시가 달라지면 의미 보존 최적화 통과로 처리하지 않는다. 원인을 기록하고 해당 변경을 분리한다. 부동소수점 구현·실행 엔진 변경 등으로 차이가 불가피하면 별도 품질 평가를 승인받는다.
- 사용자 승인, 노출·꼬리 확인, 무결성 검사, 최종 기록, 오류·취소 처리를 유지한다.
- IP 전환 일정·어댑터 적용 횟수와 모델 해제 순서를 확인한다. 캐시로 일부 인코더를 건너뛰면 기존 오프로딩 훅의 순서도 달라질 수 있다.
- 단위·통합 테스트 후 승인된 GPU 확인을 진행한다. CPU 테스트 성공을 GPU 출력·메모리 검증으로 대신하지 않는다.
- 현재 코드의 reserved 6.5 GiB 제한을 조용히 완화하지 않는다. 실제 착수 시 학습 후 설정과 검증 계약을 다시 확인한다.
- 최소 사양 목표인 VRAM 8GB·RAM 16GB는 출시 보장 결과가 아니다. 지원 환경별 설치·생성 보장은 뒤의 배포 호환성 단계에서 확인한다.
- 취소·실패 후 재실행, 반복 요청의 활성 메모리 증가, 캐시 상한 준수를 확인한다.
- 개선되지 않은 항목과 남은 병목도 보고한다. 수치 없는 “메모리 최적화 완료”로 종료하지 않는다.

실행 결과에는 기준 환경, 시나리오, 수정 전후 구간별 시간·메모리, 캐시 적중/무효화, 출력 동일성, 실패·취소, 미측정 이유를 남긴다. 1순위 완료 후 2순위 필요 여부를 다시 결정한다.

### 9.3 별도로 확인한 작업 공간 정리 누락

이전 GUI 요청은 생성 뒤 자동 머리 붙이기를 시작하기 전에 중단됐다. 남은 사용량은 9,568,256 bytes, 예약량은 23,068,672 bytes였다. 이번 사례의 중단 지점은 정상 생성 뒤의 단계 전환이며, 취소 뒤의 오류로 혼동하지 않는다.

모델 참조와 일반 캐시를 정리해도 GPU 행렬 계산 라이브러리의 작업 공간은 별도 풀에 남았다. 설치된 PyTorch 2.9.1+cu128의 기본 cuBLAS 작업 공간 8,519,680 bytes와 cuBLASLt 작업 공간 1,048,576 bytes의 합계가 잔여 사용량과 같다. [해당 버전의 PyTorch 소스](https://github.com/pytorch/pytorch/blob/v2.9.1/aten/src/ATen/cuda/CublasHandlePool.cpp)에 두 작업 공간의 보관·해제 구현이 있다.

기존 정리 함수에 계산 완료 대기 → 작업 공간 해제 → 일반 캐시 반환 순서를 추가했다. 실제 모델 할당이 남으면 기존 중단 기준을 계속 적용한다. 내부 API를 쓰므로 PyTorch 버전을 바꿀 때 지원 여부와 정리 동작을 재검증한다.

- CPU 테스트 168개 통과: 작업 공간만 남은 경우 정상 진행, 모델 할당이 남은 경우 계속 중단, 정리 실패와 출력 폐기 동작을 확인했다.
- 작은 GPU 계산 2회: 이미지 모델을 적재하지 않고 GUI 오류와 같은 잔여 용량을 재현했다. 수정한 정리 뒤 두 번 모두 사용·예약 0 bytes였다.
- 이번 GUI 실행: 자동 머리 붙이기 4장이 완료됐고 부모 앱의 종료 사용·예약 값도 0이었다.
- 아직 미확인: GUI 취소 후 재생성, 장기 반복 요청, 이 수정 전후의 생성 이미지 SHA 대조.

이 수정은 자원 반환 누락을 고친 것이다. 이번 16분 10초 처리 시간을 줄였다는 증거로 사용하지 않는다.

### 11.6 구현 — 재시도에 작업 프로세스 재사용(세션), 기본 꺼짐 (D-180)

> 사용자 10/24: 기존 준비 작업을 재사용하는 최소 구현. 모델뿐 아니라 요청 사이 상태가 남는 문제를 다룬다 — seed·입력 이미지·프롬프트·어댑터·임시 상태의 초기화와 실패·취소 뒤 정리. 같은 프로세스에서 다른 요청을 이어 해도 섞이지 않아야 한다.

**범위:** 자유 생성(②)의 재시도만. 재시도 요청은 seed만 다르다(요청 37 기록). ① 의상 편집과 ②의 첫 시도는 지금처럼 각각 새로 준비한다. ①→② 전환 재사용은 넣지 않았다 — 지시문이 달라 문장 인코더를 다시 올려야 하고, 그 순간 최고 6.37GiB가 불러 둔 파이프라인과 겹칠 수 있어 측정 없이 넣지 않는다.

**요청 사이 상태:**

| 항목 | 다음 요청에 넘김 | 근거·확인 |
|---|---|---|
| GGUF 변환기·VAE·블록 오프로드 설정 | 넘김 | 같은 가중치(첫 작업이 검사한 파일로 불러 둠). 작업 사이에는 VAE를 CPU로 내리고 GPU 캐시를 비움 |
| 문장 임베딩(CPU) | 넘김 | 지시문·입력 그림이 같을 때만. 조건 그림을 다시 만들어 첫 작업과 SHA 대조 |
| 모델 파일 검사 기록 | 넘김(`files_rechecked: false`) | 파일을 다시 읽지 않으므로 다시 검사하지 않음. 새 프로세스는 언제나 전체 검사 |
| seed·생성기 | **새로** | 요청의 seed로 CPU 생성기를 새로 만듦 |
| 입력 그림 | **새로** | 다시 읽고 SHA 확인 |
| 지시문 | 같아야 함 | 다르면 세션에 보내지 않음(새 프로세스) |
| 어댑터(가속 LoRA·그림체 LoRA) | **세션 대상 아님** | 어댑터를 붙인 요청은 세션을 쓰지 않음 |
| model_inputs·진행·미리보기·단계 기록·메모리 감시·상한 | **새로** | 요청 폴더마다 |
| 전처리 감시 함수 | **새로** | 작업이 끝나면 원래 함수로 되돌리고 다음 작업에서 새로 감쌈 |
| 스케줄러 상태 | **새로** | 파이프라인 호출이 단계를 새로 정함 |

- **같은 프로세스에서 다른 요청:** 재사용 열쇠 = 요청에서 seed만 뺀 내용(`reuse_key`). 실행기는 열쇠가 다른 요청을 세션에 보내지 않고 새 프로세스로 돌린다. 작업 프로세스도 다시 확인해 다르면 멈춘다.
- **실패·취소·메모리 중단:** 그 작업의 기록을 남기고 넘길 것을 모두 버린 뒤 프로세스가 끝난다. 실행기도 세션을 끝낸다. 다음 요청은 새 프로세스.
- **실행기가 사라지면:** 표준 입력이 닫히는 것을 보고 바로 끝난다. 다음 작업이 30분 안에 없어도 끝난다.
- **기록 경쟁:** 작업 프로세스가 요청 폴더의 최종 기록 두 개를 다 쓴 뒤 완료 표시(`job-N.done.json`)를 남기고, 실행기는 그것을 기다린다(쓰는 중인 run.json을 열지 않음).
- **기본값 꺼짐:** `GENAI_QWEN_SESSION_REUSE=1`일 때만. GPU 확인은 요청 38(승인 대기). 통과해도 기본값 켜기는 사용자 결정.
- **품질 비교:** 요청 37과 그림 SHA 일치를 먼저 본다. 다르면 자동으로 품질 실패·성공으로 처리하지 않고 원인을 조사한다(요청 38 '불일치 처리').
- **메모리:** 작업 사이 대기 중에도 세션 프로세스는 CUDA 문맥을 가진다. 결과 분석(머리 분할, PyTorch 예약 5.08GiB)과 겹치는 동안의 장치 전체·프로세스별·RAM 사용량은 요청 38에서 잰다. 예약량 차감으로 여유를 정하지 않는다.
