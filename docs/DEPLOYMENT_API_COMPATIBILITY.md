# 배포 목표와 외부 API 호환성 (2026-10-13, 사용자 확정 D-110)

> 이 문서는 배포 목표를 적는다. **이 프로젝트는 독립 실행 앱(GUI)으로 사용하며, 향후 외부 서비스에서도 API로 같은 기능을 호출할 수 있어야 한다.** 현재 구현 범위는 GUI 연결이다. API 서버와 LLM 연동은 지금 구현하지 않는다. 제품 계약은 [FLOW.md](FLOW.md), 완성 판정 기준은 FLOW.md의 "완성 판정 기준"(D-109)을 따른다.

## 결론부터
- 공통으로 유지할 것은 화면 형태가 아니라 **입력, 작업 순서, 상태, 결과의 의미**다.
- 생성 로직이 화면이나 통신 방식(확인창, HTTP)을 실행 조건으로 삼으면 한쪽에만 맞는 코드가 된다. 반대로 GUI용·API용 로직을 따로 만들면 검증·실패 처리·품질 기준이 갈라진다. 둘 다 하지 않는다.
- 아래 구조 원칙은 **지금의 변경 범위부터** 적용한다. 전체 재작성은 하지 않는다.

## 구조 원칙
1. 편집·생성·품질 판정의 작업 흐름은 GUI나 HTTP에 의존하지 않는 공통 로직으로 둔다.
2. GUI는 입력 수집, 진행 표시, 사용자 결정 전달을 맡는다. 모델 실행과 품질 판정 규칙을 화면 코드에 넣지 않는다.
3. 공통 로직은 명시적인 요청을 받고, 진행 상태와 결과를 반환한다. 결과 상태는 **완료 · 품질 미달 · 실패 · 취소 · 검토 대기**를 구분한다.
4. 사용자 확인이 필요하면 공통 로직이 확인창을 띄우지 않고 '검토 대기'와 검토 자료를 반환한다. 승인·거절은 별도의 입력으로 받는다.
5. 모델 적재·GPU 자원·파일 저장은 각각 책임을 분리한다. GUI 종료나 외부 요청 취소가 자원 정리와 어떻게 연결되는지 명시한다.
6. 향후 API도 같은 공통 로직을 호출한다. GUI용·API용 생성 로직을 중복 작성하지 않는다.
7. GUI 없이도 가벼운 대체 실행기로 작업 순서와 실패 처리를 검증할 수 있게 한다. 이것은 실제 이미지 품질 검증과 구분한다.
8. 전체 재작성은 하지 않는다. 실제 호출 흐름을 먼저 확인하고, 승인된 변경 범위부터 작은 단위로 정리한다.

## 현재 구현과의 대조 (원본 편집형 옷 바꾸기 경로, 2026-10-13 기준)
사실 확인용 표다. "맞음"은 원칙을 이미 따른다는 뜻이고, "정리 필요"는 다음 변경 때 작은 단위로 고칠 항목이다. 이 표로 기능이 연결됐다고 간주하지 않는다.

| 원칙 | 현재 상태 | 근거 |
|---|---|---|
| 1 공통 로직 | 맞음 | `genai_lab/outfit_edit_pipeline.py: run_outfit_pipeline`이 캔버스 준비 → 부위 분할 → Qwen 편집 → 팔 검사 → 머리 합성 → 재시도를 모두 맡고, PySide·HTTP를 가져오지 않는다. 검사 규칙은 `genai_lab/outfit_edit.py`. |
| 2 GUI 역할 | 대체로 맞음 | `genai_lab/studio_controller.py`는 입력을 모으고 `run_outfit_pipeline`을 `QThread`에서 부르며 진행 문구만 표시한다. 품질 판정 규칙은 화면 코드에 없다. |
| 3 요청·상태 | 부분 | 요청은 `OutfitEditSpec` → `make_outfit_request` → `validate_outfit_request`로 명시적이다. 결과 상태는 `composited`(완료 / 품질 미달)와 예외(실패)·`RuntimeError("사용자가 취소했습니다.")`(취소)로 표현되며, 검토 대기는 `OutfitEditResults.status = "awaiting_user_review"`다. **정리 필요:** 다섯 상태를 한 가지 이름 체계(예: 결과 사전의 `status` 값)로 통일하는 일. |
| 4 확인창 분리 | 부분 | 결과 검토·승인·저장은 `genai_lab/outfit_edit_results.py: OutfitEditResults`(GUI 의존 없음)가 맡고, 승인은 `approve(checks)`라는 별도 입력이다. **정리 필요:** 시작 전 확인(성별·30분 안내)은 `studio_controller.confirm_outfit_edit`가 `QDialog`를 직접 띄운다 — 공통 로직이 아니라 GUI 쪽이므로 원칙 위반은 아니지만, API에서는 같은 확인 항목(성별, 머리 장식)을 요청 입력으로 받아야 한다. 확인 항목 목록을 공통 모듈로 옮기는 일. |
| 5 자원 분리 | 맞음 | Qwen은 별도 venv 작업 프로세스(`qwen_pose_worker`), 부위 분할·관절 인식은 하위 프로세스로 돌고 끝나면 내린다(GUI 프로세스는 CUDA를 잡지 않음). 취소·시간 초과 시 하위 프로세스를 `terminate/kill`한다. 저장은 `OutfitEditResults.export`가 따로 맡는다. **명시할 것:** GUI 종료 시 진행 중인 작업 프로세스 정리 경로(현재 `cancel` → `cancelled()` 신호 → 하위 프로세스 종료). |
| 6 중복 금지 | 맞음 | GUI(`studio_controller`)와 확인 실행기(`scripts/outfit_edit_gpu_check.py`)가 같은 `run_outfit_pipeline`을 부른다. |
| 7 가벼운 실행기 | 맞음 | `scripts/outfit_edit_gpu_check.py`가 GUI 없이 같은 흐름을 돌리고 `summary.json`·검토 그림을 남긴다. CPU 테스트(`tests/test_outfit_edit_pipeline.py`)는 가짜 Qwen 결과로 작업 순서·재시도·거부 이유를 검증한다. 이미지 품질 검증(GPU 시험·사용자 판정)과는 구분한다. |
| 8 작은 단위 | 적용 중 | 1단계 정리(미사용 모듈 삭제, c4ecd2a1) 완료. 2·3단계 정리는 사용자 결정 후. |

## 향후 API에서 같은 기능을 부를 때의 뜻
구현은 하지 않지만, 공통 로직이 받는 것과 돌려주는 것은 이미 다음과 같다. API는 이것을 그대로 감싼다.
- 입력: 캐릭터 그림, 의상 그림, 머리 장식 유지 여부(지금은 항상 유지), 캐릭터 성별(male/female/unspecified), 실행 환경 설정 파일.
- 진행: 단계별 상태 문구(`progress`), 취소 신호(`cancelled`).
- 결과: 합성 여부, 거부 이유(머리 위치·형태·팔), 시도 기록, 결과·Qwen 원본 파일 경로와 SHA, 검사 수치. 검토 대기 → 승인(`approve`) → 저장(`export`)은 별도 입력이다.
- 외부 LLM(자세 문장 등)은 자유 생성 단계에서 계약을 갱신할 때 정한다. Qwen 지시문은 코드 안의 고정 문장이며 LLM·사용자 입력이 아니다(D-108).

## 변경 규칙
- 이 문서의 원칙을 어기는 변경(예: 공통 로직에서 확인창 호출, 화면 코드에 판정 규칙 추가)은 하지 않는다.
- "정리 필요" 항목은 기능 변경과 섞지 않고 따로 작은 커밋으로 한다. 각 항목은 CPU 테스트로 작업 순서·실패 처리를 확인한다.
- API 서버·LLM 연동을 시작할 때 이 문서를 갱신하고 FLOW.md 계약을 다시 승인받는다.
