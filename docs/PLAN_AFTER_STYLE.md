# 그림체 학습 이후 계획 (2026-10-27 회의 기록)

> 사용자와 Claude의 회의(10/26~10/27) 기록이다. 다른 대화와 섞이지 않도록 결정과 근거, 아직 정하지 않은 것을 나눠 적는다. 지금 할 일은 [ROADMAP.md](ROADMAP.md) '지금 지도'가 기준이다.

## 1. 확정한 순서 (사용자, 10/27)

1. **그림체 학습**: 클라우드 결과(v8까지 진행, 사용자 10/27) 확인. 이 PC에서 LoRA를 붙였을 때의 메모리 최고치·단계당 시간을 먼저 잰다.
2. **메모리 최적화**: 그림체 LoRA가 들어간 상태로 다시 잰다. 6.5GiB 상한은 유지한다. 넘치면 상한을 올리지 않고 붙이는 방식(합치기·블록과 함께 옮기기)을 바꾼다.
3. **배포 설치 완성**: 설치형 앱과 최초 모델 준비. 여기까지가 '제품 완성' 확인선이다.
4. **자동학습(연구)**: 3까지 완성된 것을 확인한 뒤 시작한다. 연구 단계라 성공이 보장되지 않고, 중간에 포기할 수 있다. 포기해도 1~3의 결과는 남는다.

- 사용자 원문: "자동학습은 하다가 포기할 수 있어 아직 연구단계이고 성공한다는 보장은 없으니까 안전하게 메모리 최적화 배포 설치까지 할 수 있지까지 보고 해야 될 거 같아"

## 2. 남은 불안 요소: 처음 보는 이미지의 동일성

- 그림체는 방향이 확정됐다(사용자). 남은 불안은 **다운로드 폴더에 없는, 진짜 처음 보는 이미지에서도 동일성이 유지되는가**다.
- 사용자 관찰: 텍스트는 정답 문자열을 저장하고 비교할 수 있다. 이미지는 숫자로 바뀌어 다시 그려지고, 그 과정에서 세부가 깎인다(오염). 그래서 그림마다 조정해 왔는데, 분류군을 만들어도 경우의 수가 너무 많다.
- 실제 구조: Qwen 편집 모델은 입력을 두 갈래로 받는다.
  - 픽셀에 가까운 압축(VAE): 세부가 남지만, 자세나 옷을 바꾸면 그대로 쓸 수 없다.
  - 의미 요약(VL 인코더): 바뀐 자세에도 쓸 수 있지만, 세부가 깎인다.
  - 많이 바꿀수록 요약에 기대게 되어 세부가 사라진다.

### 동일성이 깨지는 3가지와 맞는 해법

| 실패 | 예 | RAG로 고쳐지나 | 맞는 해법 |
|---|---|---|---|
| ① 설정·조건 선택 오류 | 다른 참조 방식·문장이 맞았는데 기본값을 씀 | 고쳐짐 | RAG(비슷한 과거 성공 사례의 설정) |
| ② 특징 추출 실패 | 처음 보는 머리 모양·꼬리·눈을 놓침 | 안 고쳐짐 | 분석·검증 보강 |
| ③ 모델이 조건을 안 따름 | 생성 중 얼굴·색 표류 | 안 고쳐짐 | 검증 후 재시도, 캐릭터별 학습 |

- 사용자는 동일성 대책으로 RAG를 택했다. RAG는 새 이미지를 저장소에 더하는 방식이고, 그 자리에서 학습해 반영하지는 않는다.
- 10/13 검토(RAG_FEASIBILITY_REVIEW) 때는 실패 대부분이 ③, ①은 1건이었다. 지금 비율은 다시 재야 한다.
- **측정 방법**: 조정에 쓰지 않은 새 캐릭터 10~20명(성인, 사용 가능한 이미지)을 현재 파이프라인으로 돌려 판정하고, 실패를 ①②③으로 나눈다. 이 묶음 결과로 로직을 고치면 다음 시험 때는 새 묶음이 필요하다.

## 3. 자동학습 구상 (4단계, 연구)

- LLM의 두 방식을 이미지에 옮긴다.
  - (가) 성공할 때까지 돌리기: 생성 → 검증 → 재시도. 가중치는 그대로.
  - (나) 성공한 것으로 다시 학습: STaR·ReST처럼 합격본만 모아 재학습.
- 흐름:
  - 낮: 생성 → 자동 검증 → 실패면 재시도 → 합격만 사람에게 보여 줌 → RAG에 기록
  - 밤: 쌓인 합격본으로 캐릭터 LoRA 갱신
  - 다음 날: 성공률이 올라 재시도가 줄어듦
- **규칙 대신 학습된 비교**를 쓴다.
  - 동일성 판정과 RAG 검색은 이미지 임베딩 유사도로 한다. 얼굴·머리를 잘라 원본과 비교하므로, 원본이 '정답 그림' 역할을 한다.
  - 규칙은 안전 기준·지원 범위처럼 꼭 지킬 것만 남긴다.
- **핵심 위험**: 검증기가 부정확하면 (가)는 잘못된 성공을 고르고, (나)는 그 오차를 학습해 키운다.
- **시작 조건**: 검증기와 사람 판정의 일치율을 기존 판정 기록으로 먼저 잰다. 예) 검증기 '합격' 중 사람도 합격인 비율 95% 이상이면 (가)를 자동으로 돌린다. (나)는 사람 표본 확인과, 처음 보는 묶음 성적이 떨어지면 되돌리는 장치를 갖춘 뒤에만 한다.
- **접는 기준**: 시작 전에 고정한다. 예) 일치율이 기준 미달이면 중단.
- **판정 단위**: 시도 1회의 속도가 아니라 **합격 1장당 시간**으로 본다. LoRA 때문에 시도가 조금 느려져도 성공률이 오르면 전체 시간은 준다.

### 자동학습이 더하는 부담 (추정, 측정 전)

| 추가되는 것 | 메모리 | 속도 |
|---|---|---|
| 캐릭터 LoRA | GPU 수백 MB 가능 — 6.5GiB 상한에서 실측 필요 | 단계마다 조금 |
| 그림체 + 캐릭터 LoRA | 약 2배(미리 합치면 1개 수준) | 약 2배 |
| 임베딩 검증 | 생성과 따로 돌리면 0 | 시도당 수 초 |
| RAG 저장소 | 이미지당 수 KB | 무시할 수준 |
| 밤사이 학습 | 낮 작업에는 0 | 같은 GPU라 생성과 동시에는 못 함 |

## 5. 나중에 할 정리 (보류)

- **연구 문서·개별 모델 정리**: 일부는 제품 로직에 들어갔지만, 여러 개가 각자 다른 모델로 따로 논다. 연구로는 가치가 있지만, 제품(면접관 시각)으로는 계층화가 안 된 구조다.
  - 제품 진입점(`gui_main.py`·`run.py`·API)에서 실제로 불러오는 모듈을 기준으로 '제품 경로 / 따로 있음 / 안 씀' 표부터 만든다.
  - 층: 진입점 → 작업 흐름 → 기능 모듈 → 기반. 연구 기록은 따로 보관하고 지우지 않는다.
- **이력서 두 갈래**(개인 작업, 제품 범위 밖)
  - (가) ML 회사용: 이 프로젝트
  - (나) LLM 백엔드용: 이 이미지 모델을 API로 쓰는 서버. 아직 만들지 않았다. 사용자: 이미지 생성 AI 완성이 먼저다.
