# 수치와 증거 중심 문서 규칙

## 목적

이 프로젝트의 설명은 “빠르다”, “좋다”, “많다”, “거의 같다” 같은 표현만으로 결론을 내리지 않습니다. 측정 가능한 내용은 값과 단위를 기록하고, 결론을 확인할 수 있는 로그·명령·파일·공식 문서를 함께 남깁니다.

## 적용 범위

이 규칙은 다음 기록에 적용합니다.

- 메인 `README.md`
- `docs/` 아래 설계·결정·문제 해결 문서
- 테스트와 성능 확인 결과
- 모델·라이브러리 선택 근거
- 사용자에게 전달하는 작업 완료 설명

## 필수 규칙

1. 측정 가능한 값에는 숫자와 단위를 함께 씁니다.
   - 시간: `159.6초`
   - 이미지 크기: `768×1344픽셀`
   - GPU 메모리: `8.0GB`
   - 파일 수: `24개`
   - 테스트 결과: `11개 통과, 0개 실패`

2. 숫자에는 측정 조건을 함께 씁니다.
   - GPU 이름
   - 모델과 버전
   - 입력 이미지 크기
   - 반복 횟수
   - 실행 날짜
   - 사용한 설정 파일

3. 결론에는 확인 근거를 연결합니다.
   - 로그 파일 경로와 실행 ID
   - 재현 명령
   - 테스트 파일과 테스트 이름
   - 설정 파일과 설정값
   - 공식 문서 링크
   - 사용자 수동 평가 결과

4. 전후 비교에는 두 값을 모두 씁니다.
   - 잘못된 예: “실행 속도가 빨라졌습니다.”
   - 올바른 형식: “동일 입력에서 실행 시간이 변경 전 160초, 변경 후 95초로 65초 감소했습니다.”

5. 측정하지 않은 값은 추측하지 않습니다.
   - `미측정`
   - `확인 불가`
   - `표본 부족`
   - `사용자 평가 전`

6. 주관적인 품질은 평가 기준과 표본 수를 함께 씁니다.
   - 평가 항목: 얼굴 유지, 의상 유지, 손 모양, 신체 비율
   - 평가 척도: 항목별 1~5점
   - 표본 수: 생성 이미지 3장
   - 통과 기준: 3장 중 2장 이상이 항목별 4점 이상

7. 한 번의 성공을 전체 성공으로 확대하지 않습니다.
   - 공식 예제 1장 성공
   - 실제 사용자 입력 1장 실패
   - 대표 입력 검증 상태: `표본 부족`

8. 모델과 라이브러리는 정확한 식별자를 씁니다.
   - 모델 저장소 ID
   - 파일명
   - 버전
   - 계산 형식
   - 라이선스
   - 설치 위치

## 수치로 표현할 수 없는 내용

구조의 목적이나 사용자 결정처럼 숫자로 직접 표현할 수 없는 내용은 숫자를 만들지 않습니다. 대신 결정 날짜, 관련 파일, 선택한 방법, 제외한 방법과 확인 근거를 기록합니다.

예:

```text
결정: 자세 제어 기능(ControlNet) 보류
결정 날짜: 2026-08-25
선택 근거: 다른 참조 이미지 시험에서 캐릭터 유지 결과가 개선됨
시험 이미지 수: 2장
정량 평가: 미측정
다음 확인 조건: 자세 참조 단계 시작 전 비교 시험
```

작업 완료 설명에는 최소한 다음 값을 포함합니다.

- 변경 파일 수
- 추가·삭제된 코드 줄 수 또는 변경 범위
- 실행한 테스트 수와 성공·실패 수

- 아직 측정하지 않은 품질 항목

## 사용자 시나리오와 처리 순서 중심의 서술

README·구조·흐름 설명은 문제와 사용자 행동에서 시작합니다. 함수나 변수 이름은 설명 뒤에 구현 위치를 확인하는 용도로 적습니다. 본문은 다음 순서로 씁니다.

1. 어떤 사용자가 어떤 입력으로 무엇을 하려는가.
2. 입력에서 무엇을 확인하고, 실패하면 무엇을 보여 주는가.
3. 어떤 정보를 추출하고 다음 단계로 무엇을 넘기는가.
4. 사용자가 확인한 값과 모델이 만든 결과를 어떻게 구분하는가.
5. 무엇을 저장하고, 어떤 조건에서 저장하지 않는가.
6. 수정 전후 무엇이 달라졌으며 어떤 기록으로 확인했는가.

영어 용어는 처음 나올 때 역할을 설명합니다. 예를 들어 seed는 ‘난수 시작값’, hash는 ‘파일 내용이 같은지 확인하는 식별값’으로 설명한 뒤 필요한 코드 이름을 병기합니다. 초안의 변수 목록을 그대로 제품 소개로 사용하지 않습니다.

수치는 반드시 분모·단위·실행 조건·평가 방법·원본 위치를 함께 둡니다. 자동 테스트 통과 수, 실제 생성 재현 수, 육안 품질 평가 수는 별도 표로 적습니다. 품질 109/120을 쓸 때는 무엇이 일치했는지와 누가 평가했는지 적고, 캐릭터·의상·자세가 모두 성공한 비율처럼 바꾸지 않습니다.

‘보이는 결과’, ‘검사 후 결과’는 제외된 원시 결과가 있는지 확인합니다. 검사 후 노출 0건을 생성 전체의 노출 0건으로 옮기지 않습니다. 진행 중인 시험은 기존 결과와 구분하고, 완료 기록을 확인하기 전에는 성과에 포함하지 않습니다.

과거 설계와 현재 코드가 다르면 문서 상단에 차이를 표시합니다. 문서 편집만으로 제품 계약을 바꾸지 않으며, 잠긴 실험 계획·라벨·원시 결과는 덮어쓰지 않습니다. 공개 저장소에서 접근할 수 없는 실험은 외부 독자가 읽을 수 있도록 조건과 수치를 문서에 옮기되, 원본 공개 여부를 분명히 적습니다.

프로젝트 소개와 기술 설명에는 질문형 제목이나 독자에게 말을 거는 문장을 쓰지 않습니다. 제목은 다루는 내용을 직접 명시하고, 본문은 작성자가 수행한 작업·근거·결과를 서술합니다. 사용자 화면의 실제 질문 문구나 설문 항목을 인용하는 경우는 구분해서 표기합니다.
