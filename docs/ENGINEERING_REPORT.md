# 문제를 발견하고 제품 동작으로 연결한 과정

입력 분석·이미지 생성·사용자 승인 과정에서 발생한 문제와 수정 결과를 정리했습니다. 근거는 2026-10-04까지 확인한 코드와 기존 실행 기록입니다. 이번 문서 작업에서 이미지를 생성하거나 측정을 반복하지 않았습니다.

## 출발점: 모델이 이미지를 만드는 것과 사용자가 제품을 쓰는 것은 달랐다

프로젝트의 입력은 캐릭터 이미지 한 장과 의상 이미지 한 장입니다. 사용자는 캐릭터가 같은 모습을 유지하면서 새 옷을 입은 결과를 원합니다. 개발 과정에서는 모델 호출이 성공하더라도 의상 일부가 바뀌지 않거나, 캐릭터 특징이 달라지거나, 화면이 이전 생성 경로를 호출하는 문제가 따로 나타났습니다.

검증은 세 부분으로 구분했습니다. 첫째는 입력 조건이 모델에 의도대로 전달됐는지, 둘째는 실제 그림이 목표에 맞는지, 셋째는 사용자가 GUI에서 확인하고 저장하는 과정이 연결됐는지입니다. 어느 한 부분이 통과했다고 나머지가 자동으로 통과하는 것은 아닙니다.

## 사례 1. 생성 모듈 성공이 GUI 성공으로 이어지지 않은 문제

### 문제와 원인

새 1회 생성 모듈은 캐릭터와 의상을 함께 만드는 방식이었지만, 기본 생성 버튼에는 이전의 캐릭터 Base 선택·의상 정밀화 흐름이 남아 있었습니다. 사용자는 의상이 바뀌기 전 캐릭터 후보를 보고 완성 이미지로 오해할 수 있었습니다. 정밀화 오류 시 승인했던 Base가 표시되는 문제도 있었습니다.

핵심은 모델의 성능이 아니라 **화면에서 시작한 요청이 어느 실행 경로로 가는지**였습니다. 생성 함수를 직접 호출하는 시험만으로는 기본 버튼의 연결 오류를 확인할 수 없었습니다.

### 처리

기본 버튼이 작업실 제어기를 거쳐 입력 분석·사용자 확인·4장 생성·결과 승인·저장으로 이어지도록 연결했습니다. 이전 경로는 별도로 구분했습니다. 화면에는 생성 중, 결과 확인 전, 사용자 확인 완료, 저장 완료를 다르게 표시합니다.

승인도 이미지 한 장에 묶었습니다. 후보를 바꾸면 승인이 해제되고, 저장할 파일이 승인 이후 바뀌면 내보내기를 거부합니다. 실패·취소 중 남은 원시 이미지는 진단 기록으로 남기되 완성된 결과 묶음으로 승격하지 않습니다.

### 확인한 결과와 한계

[작업실 테스트](../tests/test_studio_generation.py)의 `test_create_button_to_review_and_export_without_legacy_fallback`은 실제 Qt 버튼 신호에서 시작해 요청 조립, 가짜 생성기, 후보 선택, 승인, 파일 저장까지 검사합니다. 별도 테스트로 확인 취소 시 생성하지 않는지, 실패 시 Base를 완성본으로 제시하지 않는지, 승인 전 저장과 덮어쓰기를 막는지 확인합니다.

GUI 연결 당시 전체 회귀는 1,463개 통과였고, 꼬리 문구 검증까지 보완한 최근 회귀는 1,529개 통과입니다. 두 수치 차이를 이미지 품질 향상으로 해석하지 않습니다. 실제 CPU 분석 연결은 당시 캐릭터·의상 한 조합에서 확인했으며, 이 연결 시험은 GPU 생성 품질 평가와 구분합니다.

근거: `outputs/gui-onepass-20261004/results.md`, [현재 사용자 흐름](CODE_FLOW.md), [작업실 구현](../genai_lab/studio_controller.py).

## 사례 2. 출력은 같은데 GPU 메모리 한도를 넘어 요청이 중단된 문제

### 문제와 원인

생성 모듈을 실제 환경에서 확인할 때, 설치된 Diffusers가 새 단계 종료 콜백 인자를 지원하지 않아 모델 적재 전에 멈췄습니다. 콜백은 매 생성 단계가 끝났을 때 얼굴 참조 강도를 전환하고 취소를 확인하는 연결 지점입니다.

검증용으로 구식 콜백에 같은 동작을 연결하면 이전 시험 이미지와 해시는 같았지만, GPU 예약 메모리가 6.52~6.56 GiB로 설정 한도 6.5 GiB를 넘었습니다. 자세 어댑터가 모델을 GPU에서 내리는 순서에 빠져 있어, 필요한 계산이 끝난 뒤에도 GPU에 남는 경로가 원인으로 확인됐습니다.

### 처리

설치된 호출 형식에 맞는 콜백을 선택하고 어떤 방식을 사용했는지 기록하도록 했습니다. 얼굴 참조의 실제 적용 단계가 같다는 것도 따로 관측합니다. 또한 모델을 GPU에서 내리는 순서에 자세 어댑터를 포함했습니다. 한도를 올려 실패를 숨기는 방식은 사용하지 않았습니다.

### 확인한 결과와 한계

수정 후 기록된 예약 메모리는 **6.375~6.414 GiB**로 6.5 GiB 이내였습니다. 자세 적용 5건과 4개 seed 요청에서 원시 이미지 해시가 각각 **5/5, 4/4** 일치했습니다. 자세 미적용 경로 2건도 일치했고, 초기 얼굴 참조 강도를 달리한 진단 1건도 일치했습니다.

장비는 RTX 4060 8GB, 이전 검증 기록의 환경은 torch 2.9.1+cu128·Diffusers 0.38.0입니다. 해시 일치는 해당 장비·모델·입력·설정에서의 재현 근거이며, 다른 GPU에서도 같은 바이트를 보장한다는 뜻은 아닙니다. 예약 메모리는 PyTorch가 확보한 공간으로, 시스템 RAM이나 GPU 전체 점유량과 동일하지 않습니다.

근거: `outputs/stage4-verify-20261001/results.md`와 `outputs/impl-verify-20261002/results.md`. 구현은 [생성 모듈](../genai_lab/onepass_generation.py), 설정은 [생성 설정](../genai_lab/onepass_generation_settings.py)에서 확인합니다.

## 사례 3. 꼬리 이름을 전달했는데 원본의 색·무늬가 달라진 문제

### 문제와 시험

라쿤 캐릭터의 원본에는 하늘색 바탕과 남색 줄무늬 꼬리가 하나 있었지만, 생성에서는 갈색 꼬리나 꼬리 두 개가 나타났습니다. 처음에는 일반 꼬리 태그와 종 이름 태그를 함께 넣어서 중복됐을 가능성을 생각했습니다.

2026-10-04 시험은 캐릭터 1명, 같은 seed 4개로 네 조건을 비교했습니다. 현재 태그, 일반 태그 제거, 색·무늬 추가, 종 이름 대신 색·무늬 사용을 나눴습니다. 기본 조건 4장은 기존 결과를 재사용했고 나머지 조건을 비교했습니다.

| 조건 | 꼬리 2개 이상 | 원본 같은 하늘색·줄무늬 꼬리 | 갈색 꼬리·덩어리 |
|---|---|---|---|
| 기존 태그 | 2/4 | 0/4 | 2/4 |
| 일반 꼬리·동물 귀 태그 제거 | 2/4 | 0/4 | 2/4 |
| 종 이름을 두고 색·무늬 추가 | 1/4 | 3/4 | 1/4 |
| 종 이름 대신 색·무늬 사용 | 1/4 | 3/4 | 0/4 |

단순히 태그 두 개가 같은 꼬리를 두 번 만들었다는 설명은 이 표와 맞지 않았습니다. 색·무늬를 구체적으로 전달한 조건에서 원본에 가까운 결과가 늘었지만, 꼬리 중복은 남았습니다. 종 이름이 모델의 전형적인 색·무늬 해석에 영향을 줬을 가능성은 있으나, 이 작은 표본만으로 인과관계를 확정하지 않습니다. 판정자는 Claude이며 사용자 검토 전 잠정 기록입니다.

### 제품에 반영한 범위

꼬리 자동 제거 대신, 입력 확인창에서 사용자가 외형 문구를 확인하고 결과에서 개수·종류·색을 다시 검토하도록 했습니다. 미확인 문구는 적용하지 않습니다. 등록된 성별·체형·노출 태그를 입력 문구에서 검사하지만, 일반 자연어 전체를 이해하는 필터는 아닙니다.

시험의 마지막 조건은 일반 동물 귀 태그도 제거했지만 제품은 기존 귀 태그를 유지합니다. 따라서 시험 결과 3/4를 현재 기능의 성공률로 그대로 옮기지 않습니다. 현재 구현의 CPU 테스트는 문구가 요청에 전달되는지와 문구가 없을 때 기존 조건이 유지되는지를 확인합니다. 제품 구성의 GPU 검증은 별도 인수인계 대상입니다.

근거: `outputs/tail-dup-20261004/results.md`, [구현 설계](../TAIL_APPEARANCE_IMPLEMENTATION_DESIGN.md), [GPU 검증 항목](../TAIL_APPEARANCE_GPU_HANDOFF.md).

## 사례 4. Windows에서 진행 기록 파일이 충돌한 문제

Qwen은 별도 프로세스에서 실행되며 부모 프로세스가 진행 기록을 읽습니다. 읽는 중 같은 파일을 교체하면 Windows 파일 공유 방식 때문에 접근 거부가 발생할 수 있었습니다. 이를 모델 오류로 처리하면 생성은 끝났는데 결과 기록을 잃는 상황을 구분하기 어렵습니다.

진행 기록은 순번별로 새 파일에 쓰고, 종료 기록은 별도 사본을 먼저 보존하도록 바꿨습니다. 일시적인 접근 거부만 최대 대기 2초·교체 시도 최대 12회 범위에서 재시도합니다. 영구적인 저장 오류를 성공으로 바꾸지는 않습니다.

Windows SMB 검사에서 기존 교체 오류를 재현했고, 짧은 잠금은 약 0.922초 뒤 교체됐습니다. 긴 잠금에서는 오류와 최종 사본이 보존됐으며 진행 기록 **40개 발행·40개 관찰**이 확인됐습니다. 이 검사는 GPU 없이 고정 바이트 표본으로 수행했으므로 이미지 생성 품질과는 관계없습니다.

상세 재현·구현·공식 API 근거: [Windows 기록 충돌 수정](QWEN_RECORD_IO_FIX.md). 회귀 테스트: [test_qwen_record_io.py](../tests/test_qwen_record_io.py).

2026-10-01 최종 후보 구성 시험은 **캐릭터 2명 × 의상 3종 × 자세 5종 × seed 4개 = 120장**을 새로 생성했습니다. 기준 구성의 기존 120장과 비교했고, Claude가 240장을 조건을 섞은 시트에서 라벨링했습니다. 이전 시험을 본 판정자였고 체형으로 일부 조건을 알아볼 수 있어 완전한 블라인드 평가는 아니었습니다.

| 120장 기준 | 비교 전 | 후보 구성 | 해석 |
|---|---|---|---|
| 캐릭터가 같다고 판정 | 92 | 103 | 11장 증가 |
| 의상이 맞다고 판정 | 111 | 109 | 2장 감소 |
| 자세가 맞다고 판정 | 113 | 106 | 7장 감소, 사전 허용 감소 4장 초과 |

RTX 4060 8GB에서 이 시험의 이미지당 생성 시간 중앙값은 **22.0초**, 최대 GPU 예약 메모리는 **6.41 GiB**였습니다. 이것은 당시 시험의 생성 시간이며, 현재 GUI에서 입력 분석·사용자 확인·4장 생성·저장을 모두 마치는 시간은 아닙니다.

당시 보고서의 ‘보이는 예상 밖 노출 0’은 시험용 검사로 숨긴 이미지를 제외한 지표입니다. 같은 기록에 노출 때문에 숨긴 사례가 있으므로 원시 이미지 120장 전체가 안전했다는 뜻으로 쓰지 않습니다. 현재 작업실에는 그 시험용 자동 판정을 적용했다고 기록하지 않습니다.

## 근거 자료의 공개 범위

위 `outputs/` 경로는 개발 PC의 기존 실험 원문 위치입니다. 공개 저장소에 모두 포함돼 있다고 보장하지 않으며, 원본 이미지에는 별도 이용 조건과 검토가 필요할 수 있습니다. 이 문서에는 확인한 수치·조건·한계를 옮겼고, 외부 공개를 위해 원본 이미지를 새로 복사하지 않았습니다.

현재 계약 문서와 실제 작업실의 연결 차이, 자동 품질 판정의 부재, 다른 PC 설치 검증은 남은 항목입니다. 이 문서는 연구 기록을 제품 기능으로 바꾸어 적거나 진행 중인 GPU 검증을 완료로 처리하지 않습니다.
