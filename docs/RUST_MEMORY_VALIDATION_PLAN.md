## 1. 목적과 착수 조건

Python에서 반복 계산·복사·모델 적재를 먼저 줄인 뒤, 남은 CPU 처리 병목에 Rust가 도움이 되는지 검증한다. Rust 학습과 제품 채택은 구분한다. 현재 Rust가 반드시 필요한 것으로 확정된 병목은 없다.

프로젝트 순서는 동일성 계획 종료 → 학습 → 메모리 최적화 → 배포 호환성 → 연동 호환성이다. 이 문서는 메모리 최적화 단계의 준비이며, 생성 시험이나 운영 환경 설치의 승인이 아니다.

제품 실험에 들어가기 전에 다음을 확보한다.

1. 최적화한 Python 기준 구현과 같은 입력의 시간·메모리 기록.
2. 대상 함수가 전체 대기 시간에서 차지하는 비중과 호출 횟수.
3. 기존 NumPy·Pillow 등으로 충분히 개선하지 못한 이유.
4. 입력·출력·오류·소유권 계약과 실험의 자원 예산.
5. 실제 사용할 라이브러리 버전·라이선스·실행 환경. 설치가 필요하면 별도 승인.

첫 실험은 CPU 함수 하나로 제한한다. CUDA 커널, 모델 가중치 관리, Qwen 편집, 자체 할당자, GUI 재설계는 포함하지 않는다. Rust가 CPU 버퍼를 관리해도 PyTorch의 VRAM 관리가 자동으로 바뀌지는 않는다.

### 소유권과 실제 메모리 반환의 구분

Rust 객체가 해제되면 소유한 자원은 해당 정리 절차를 거친다. 그러나 할당자가 반환된 공간을 보유할 수 있으므로 프로세스의 OS 메모리 표시가 즉시 같은 크기로 내려간다고 보장하지 않는다. Python 객체 참조, Rust 버퍼 용량, 프로세스 메모리, GPU 메모리를 각각 기록해야 한다.

안전한 Rust를 기본으로 쓰고, 첫 시험에서는 자체 unsafe·사용자 정의 할당자·병렬 처리 도입을 하지 않는다. 의존 라이브러리 내부의 unsafe까지 없다는 뜻은 아니다.

## 3. 첫 실험 후보와 데이터 흐름

후보는 [상위 계획의 P7](MEMORY_OPTIMIZATION_PLAN.md)의 얼굴 크롭 주변 배열 처리다. 기존 [onepass_character.py](../genai_lab/onepass_character.py)의 여러 마스크 결합·RGB 복사 중 실제 병목으로 측정된 부분만 고른다. 함수 위치는 착수 때 다시 확인한다.

DWPose·검출기·전경 추론은 시험 범위 밖이다. 저장된 분석 결과를 입력으로 사용한다. 기존 좌표·팔 선분 그리기·턱 제한·크롭 규칙을 그대로 두고, 처음에는 이미 만들어진 마스크의 결합과 픽셀 복사처럼 작은 연산부터 검토한다. 해당 부분이 병목이 아니면 이 후보로 구현하지 않는다.

데이터 흐름:

입력 파일·분석 결과 확인 → 기존 Python 디코딩 → 배열 계약 검사 → Python 또는 Rust 처리 → 출력 비교 → 시간·메모리 기록.

성공 결과뿐 아니라 기존에 실패해야 하는 입력도 같은 의미로 실패해야 한다. 연산을 합치면서 얼굴 보존·팔 제거·승인 절차를 바꾸는 것은 최적화 범위가 아니다.

### 구현 전에 고정할 함수 계약

| 항목 | 첫 시험의 설계안 |
|---|---|
| 입력 | CPU RGB uint8 배열과 관련 마스크. 실제 dtype·shape·좌표 단위는 기존 함수에 맞춰 명시 |
| 입력 변경 | 금지. 호출 전후 값 비교 |
| 빌림 | 호출 중에만 읽기. 호출이 끝난 뒤 입력 포인터를 보관하지 않음 |
| 연속성 | 연속 배열을 기본으로 사용. 비연속 입력은 명시적으로 한 번 복사하고 그 비용을 전체 시간에 포함 |
| 동시 실행 | 동일 입력에 대한 외부 쓰기 금지. 초기 시험은 동기·단일 작업자 |
| 인터프리터 분리 | 첫 시험에서 임의 적용하지 않음. 필요하면 Rust 소유 입력 사본 또는 동시 변경 방지 계약부터 검증 |
| 출력 | 입력·재사용 작업 버퍼와 독립된 배열. Python이 보유하는 동안 이후 호출로 값이 바뀌지 않음 |
| 임시 버퍼 | 호출 전용 또는 상한이 정해진 처리 객체 소유. 두 방식을 비교 |
| 오류 | 잘못된 dtype·shape·범위는 명시적 오류. Python 기준의 공개 오류 계약 유지 |
| 취소 | 호출 전후 취소 확인. 긴 루프라면 취소 점검 구간과 반응 시간의 상한을 별도 정의 |
| 과대 입력 | 크기 곱의 오버플로와 허용 바이트 수를 할당 전에 검사. 실제 OOM을 일부러 발생시키지 않음 |

이 설계안은 실제 함수 선정 후 계약 파일로 잠근다. 기존에 지원하던 입력을 성능 측정 편의상 조용히 제외하지 않는다.

## 4. 자원 사용 정책과 선택 비용

목표는 같은 결과를 자원 예산 안에서 더 빨리 만드는 것이다. 최대 점유나 최소 점유 자체를 성공 기준으로 삼지 않는다.

| 선택 | 얻는 것 | 지불하는 것 | 검증 방법 |
|---|---|---|---|
| 호출마다 임시 버퍼 생성 | 수명이 단순하고 요청 간 보유가 적음 | 반복 할당·초기화 | 반복 시간과 할당 횟수 |
| 작업 버퍼 재사용 | 반복 할당 감소 | 이전 최대 입력만큼 용량이 남을 수 있음 | 큰 입력 뒤 작은 입력, 보유 용량·퇴출 기록 |
| 입력 배열 빌림 | 큰 복사 감소 | 외부 변경·수명 제약 | 입력 불변·동시 접근 계약 |
| Rust 소유 사본 | 소유권과 작업 분리가 명확 | 복사 시간과 추가 RAM | 경계 포함 시간·최대 RAM |
| 여러 연산 통합 | 중간 배열·메모리 왕복 감소 가능 | 코드 복잡성·경계 오류 가능성 | 픽셀 동일성·유지보수 범위 |
| 병렬 처리 | CPU 계산 처리량 증가 가능 | 스레드·메모리 대역폭 경쟁 | 단일 스레드 병목 확인 후 별도 시험 |

처리 중 계산 자원을 쓰는 것과 데이터를 오래 보관하는 것은 다르다. 반복 사용 가능성이 확인된 데이터만 보관하고, idle·오류·취소 시의 유지/해제 정책을 명시한다.

버퍼 상한은 입력 최대 크기와 허용 동시 작업 수로 계산한다. 계획 RAM은 입력 + 출력 + 동시에 살아 있는 임시 배열 + 보유 캐시로 설명하고 실제 프로세스 측정과 대조한다. 현재 총 RAM 예산은 미확정이다. VRAM 8GB·RAM 16GB는 기존 목표이며 검증된 배포 보장이 아니다. GPU 검증의 기존 reserved 6.5 GiB 제한을 이 시험에서 바꾸지 않는다.

## 5. 비교군과 실험 범위

| 비교군 | 내용 | 용도 |
|---|---|---|
| A | 현재 Python 구현 | 기존 동작·비용 기록 |
| B | 1순위 개선을 적용한 Python 구현 | Rust 채택 판단의 기준 |
| C | 같은 계약의 Rust 구현 | 경계 포함 비용과 메모리 비교 |

제품 채택은 B와 C로 판단한다. A보다만 빠르고 B보다 느리면 Rust 효과로 채택하지 않는다.

첫 시험은 함수 하나, Rust 방식 최대 두 가지(호출별 버퍼 / 상한 있는 버퍼 재사용)로 제한한다. 다중 스레드·SIMD·할당자 변경으로 계속 조건을 늘리지 않는다. 효과가 불명확하면 그 상태를 기록하고 종료한다. 추가 실험은 새 범위로 정한다.

### 단계별 실행·중단

| 단계 | 작업 | 다음 단계 조건 |
|---|---|---|
| 0 | 최적화한 Python 프로파일, 대상·자원 예산·입출력 계약 확정 | 실제 병목과 전체 영향 설명 가능 |
| 1 | Linux에서 순수 Rust 함수와 단위 테스트 작성 | 정답·경계·오류 테스트 통과 |
| 2 | Python 연결과 소유권 검증 | 입력 불변, 출력 수명, 예외 전달 통과 |
| 3 | Windows 대상 CPU 비교 | 결과 동일, 시간·메모리 기록 완비 |
| 4 | 승인된 앱 통합 검증 | 기존 출력·오류·취소·자원 제한 유지 |
| 5 | 채택 또는 보류 기록 | 전체 이득·배포 비용·남은 한계 명시 |

코딩·코드 수정은 Linux에서만 한다. Windows는 프로젝트 보관·문서 작업·테스트에 사용한다. 환경·패키지·빌드 도구 설치는 승인 후 진행한다. Codex의 GPU 실행은 현재 범위 밖이다.

## 6. 정확성·수명 테스트 계획

테스트 이름은 예정 이름이다. 아직 구현하거나 실행하지 않았다.

| ID | 입력·상황 | 확인할 결과 |
|---|---|---|
| T01 기준 결과 | 승인된 기존 입력·저장 분석 결과 | B/C 배열 dtype·shape·픽셀 일치, 크롭 위치·실패 사유 일치 |
| T02 마스크 경계 | 빈 마스크·전체 마스크·단일 픽셀·모서리 접촉 | 기준 함수와 결과/오류 동일 |
| T03 크기·범위 | 1픽셀·홀수 크기·직사각형·허용 최대·잘못된 좌표 | 범위 밖 접근 없음, 정한 오류 계약 |
| T04 배열 배치 | 연속·전치·간격 슬라이스·역순·읽기 전용 | 명시한 복사/처리 정책, 값 동일, 복사 바이트 기록 |
| T05 입력 불변 | 호출 전후 원본·마스크 비교 | 변형 0, 입력 변경 금지 준수 |
| T06 출력 수명 | 첫 결과를 보유한 채 다음 호출·작업 객체 해제 | 첫 결과가 그대로 읽히고 다음 결과와 값이 섞이지 않음 |
| T07 입력 수명 | 호출 후 입력 참조 해제, 출력 계속 사용 | 결과가 입력의 수명에 매달리지 않음 |
| T08 버퍼 정책 | 큰 입력 → 작은 입력 → 반복 → 명시적 정리 | 상한 준수, 용량 유지·퇴출이 정책과 일치 |
| T09 실패·취소 | 검증 실패·취소 요청·실패 후 정상 호출 | 최종 상태 기록, 상태 오염 없음, 안전한 시점에서 정리 |
| T10 자동 입력 | 고정 seed의 다양한 배열·좌표 조합 | 기준 구현과 대조, 실패 입력 축소·저장 |
| T11 경계 위반 | dtype·채널 수 오류·할당 상한 초과 | 할당 전 예측 가능한 오류, 프로세스 강제 종료 없음 |
| T12 배포 | 대상 Windows 환경에서 wheel 설치·import·CPU fixture | 개발 도구가 없는 실행 환경에서도 요구 의존성으로 동작 |

소유권 위반을 유발하는 비동기 쓰기를 실제로 실행해 안전성을 시험하지 않는다. 지원하지 않는 동시 접근은 인터페이스와 호출 경로에서 차단한다. Miri는 순수 Rust 핵심의 보조 검사로만 사용한다.

실제 이미지 fixture는 사용 허가된 기존 파일에서 선택하고 목록·SHA를 고정한다. 이 프로젝트에서 사용 금지된 파일은 입력 목록에 넣지 않는다. 이미지 생성 없이 인공 배열로 경계 검사를 수행한다. 저장 파일 해시와 디코딩 픽셀 동일성은 따로 적는다.

정수 마스크·RGB 변환은 오차 0을 기본으로 한다. 부동소수 연산을 포함해야 한다면 허용 오차와 이유를 결과 확인 전에 따로 고정한다. 차이가 난 뒤 허용 오차를 늘리지 않는다.

## 7. 시간·메모리 측정 계획

### 비교 조건

같은 장치·OS·입력·버전에서 B/C를 비교한다. release 빌드를 쓰고 디버그 빌드와 비교하지 않는다. Python·NumPy·Rust·컴파일러·빌드 옵션·CPU 명령어 대상·스레드 수를 기록한다. 개발 PC 전용 명령어 최적화를 배포 가능 성능으로 주장하지 않는다.

입력은 작은 얼굴 영역, 제품 기준 해상도, 승인된 최대 입력 크기를 포함한다. 크기마다 동일 입력 반복과 서로 다른 입력 순환을 구분한다. 첫 호출, 워밍업 후, 큰 입력 처리 후를 따로 집계한다.

CPU 시간 시험의 초기 설계는 별도 프로세스 3회, 프로세스별 워밍업 5회와 측정 30회다. 짧은 함수는 타이머 해상도를 넘도록 묶음 호출하고 호출 수를 기록한다. 실행 전 예비 타이머 점검에서만 횟수를 조정하며, 그 결과를 제품 성능 결과에 포함하지 않는다. 본 측정 시작 전에 최종 횟수·순서·입력 목록을 잠근다.

B/C 실행 순서는 교차 배치한다. 중앙값·범위와 가능하면 신뢰구간을 보고하고 임의 이상치 삭제를 하지 않는다. 배경 작업·전원 모드·발열·페이지 폴트·파일 캐시가 다른 실행은 표시한다. 낮은 표본으로 장기 안정성을 주장하지 않는다.

### 시간 범위

- Rust 내부 계산 시간.
- Python 입력 검사·연속 배열 변환·Rust 호출·출력 반환을 포함한 함수 전체 시간.
- 실제 사용자 흐름의 분석 단계 및 요청 전체 시간. GPU 생성·사용자 대기와 분리.

C의 전체 시간에는 추가 복사·변환이 반드시 들어간다. 순수 계산만 빨라진 경우 전체 효과로 보고하지 않는다. 앱 전체 영향은 상위 계획의 암달의 법칙으로 예상하고, 통합 측정으로 확인한다.

### 메모리 범위

| 지표 | 측정 목적 | 해석 제한 |
|---|---|---|
| 원본·출력 배열 바이트 | 입력 규모와 필수 데이터량 | 파일 크기와 같지 않음 |
| 작업 버퍼 len/capacity·최대 용량 | 실제 계산과 보유 공간 구분 | 논리값이며 OS 메모리 전체가 아님 |
| Rust 할당 횟수·누적 바이트·최대 생존량 | 임시 할당과 재사용 확인 | dhat가 관측한 범위만 보고 |
| 프로세스 RSS/working set·private 메모리 | 앱에서 실제 보이는 점유 | OS별 정의가 다름. 공유 페이지 단순 합산 금지 |
| 호출 종료·정리 후 메모리 | 누적 증가·캐시 상한 점검 | 즉시 시작값으로 복귀해야 한다고 가정하지 않음 |
| GPU 지표 | 통합 시 기존 자원 계약 유지 | CPU 함수 시험에서 측정하지 않으면 미측정 표시 |

CPU 수명 점검은 같은 입력과 크기 교차 입력을 각각 200회 반복하는 초기 계획으로 둔다. 정책상 보유 버퍼와 살아 있는 할당의 증가를 확인한다. 유한 반복에서 증가가 없었다는 결과를 누수 부재의 증명으로 쓰지 않는다.

성능 측정은 상세 할당 추적을 끈 상태에서 한다. 메모리 분석은 별도 실행한다. 프로파일러 유무와 로그 비용을 함께 보고한다. 샘플링 사이에 짧은 피크가 지나갈 수 있으므로 관측 피크와 할당 추적 피크를 구분한다.

## 8. 사람이 읽을 수 있는 실행 기록

최종 로그는 요청 → 단계 → 함수 호출 순서로 연결한다. 기록이 없으면 0으로 대신하지 않고 미측정과 이유를 남긴다.

| 필드 묶음 | 기록 내용 |
|---|---|
| 실행 식별 | 실행 ID, 비교군, 입력 SHA, 코드·환경·정책 버전 |
| 실행 시간 | UTC 시각, 단조 시계 경과 시간, 시작·종료, PID·작업 ID |
| 처리 상태 | 성공·실패·취소, 실패 위치·이유 |
| 입력 규모 | shape·dtype·stride·연속성·읽기 전용 여부 |
| 메모리 동작 | 복사 여부·이유·바이트, 할당/재사용/확장/퇴출, 버퍼 capacity |
| 캐시 | hit/miss와 무효화 이유, 보유 바이트·상한 |
| 결과 | 픽셀 동일 여부·차이 수, 결과 파일 SHA |
| 환경 영향 | 다른 작업, 스레드 수, 샘플링 간격과 누락 |

읽는 화면에는 단계별 시간 막대와 같은 시간축의 메모리 그래프를 둔다. 구간을 선택하면 입력 크기, 복사·재사용, 호출 횟수, 정리 여부를 볼 수 있게 한다. 사용자 확인 대기는 별도 색과 구간으로 표시한다. 이는 향후 개발자용 진단 산출물 계획이며 제품 GUI에 전문 용어를 추가하는 요구가 아니다.

예를 들어 “마스크 처리에서 메모리가 늘었다”만으로 원인을 확정하지 않는다. 해당 구간의 배열 할당 기록과 버퍼 용량 증가를 함께 확인한다. 반복 호출 중 메모리가 일정한 높이에서 멈추면 보유 정책과 대조하고, 계속 증가하면 살아 있는 참조·할당을 조사한다.

원본 이미지·보존 문구 등의 내용은 로그에 불필요하게 복제하지 않는다. ID와 해시 중심으로 기록한다.

## 9. 채택·보류·중단 기준

| 결과 | 처리 |
|---|---|
| 픽셀·오류·수명 계약 불일치 | 성능 판단 중단. 최적화 성공으로 보고하지 않음 |
| 자원 상한 초과·프로세스 비정상 종료 | 해당 조건 중단. 더 큰 입력으로 밀어붙이지 않음 |
| Rust 내부만 빠르고 경계 포함 시간은 개선 없음 | 제품 채택 보류 |
| 경계 포함 시간은 개선되나 전체 영향이 작음 | 절약한 실제 시간과 유지보수 비용을 보고 결정 |
| 메모리 절감과 시간 증가가 함께 발생 | 사전 고정한 메모리 예산·허용 지연과 비교 |
| 속도 향상과 메모리 증가가 함께 발생 | 지원 환경 여유·연속 요청·다른 앱 사용 영향까지 비교 |
| 정확성 유지, 자원 예산 내, 반복 측정상 의미 있는 이득 | Windows 배포·통합 검증 후 채택 검토 |
| 결과 변동이 이득보다 크거나 필수 지표 누락 | 미확정으로 종료. 성공으로 집계하지 않음 |

착수 전에 총 RAM·버퍼 예산, 허용 입력 크기, 허용 지연 증가, 제품에서 의미 있는 최소 개선량을 기준 측정과 함께 정한다. 현재 이 값들은 미정이다. 임의로 10% 같은 성공 수치를 추가하지 않는다.

CPU 단위 시험은 새 이미지 생성 0회다. GPU 통합이 필요하면 모델·seed·실행 수·상한을 별도로 사전 등록하고 승인받는다. 기존 원시 SHA·IP 일정·어댑터 적용·메모리 제한·승인 및 취소 동작을 확인한다. 같은 환경의 출력이 달라지면 원인을 분리하고 결과를 임의로 통과시키지 않는다.

## 10. 환경·배포 검증과 산출물

Rust 코드는 Linux에서 작성하고, 대상 Windows Python에 맞는 확장 모듈로 테스트한다. Linux 바이너리를 Windows에서 그대로 쓰지 않는다. 크로스 빌드나 Windows 빌드 중 필요한 도구·SDK·라이선스를 확인한 뒤 방식을 정한다. Python ABI 지원이 NumPy 호환성까지 자동 보장하는 것으로 해석하지 않는다.

첫 실험의 산출물은 향후 승인된 outputs/rust-memory-validation-<실행일>/ 아래에 모은다. 이번에는 이 폴더나 시험 코드를 만들지 않는다.

| 파일 | 내용 |
|---|---|
| preflight.md | 대상 함수·기준 환경·병목 근거·예산·범위 |
| contract.md | 입력·출력·소유권·오류·취소·버퍼 수명 |
| criteria.md 및 SHA-256 | 확정한 입력·횟수·순서·합격 및 중단 조건 |
